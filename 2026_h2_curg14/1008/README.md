**글의 설명 순서와 Arc의 담당 범위**

- 화살표는 글의 설명 순서이며, 실제 거래의 처리 순서는 아님

```text
[1 기업 지급 결제]
    무엇을 지급하고, 언제 완료된 것으로 판단하는가
              |
              v
[2 기업 결제의 문제]
    어떤 단계에서 지연, 비용, 오류와 위험이 발생하는가
              |
              v
[3 Arc의 선택 이유]
    어떤 업무와 조건에서 Arc가 도움이 될 수 있는가
              |
              v
[4 Circle과 Arc의 연결]
    제품, 앱, 금융기관과 Arc는 각각 무엇을 담당하는가
              |
              v
[5 Arc]
    프로토콜: 거래를 어떻게 실행하고 확정하는가
    경제 구조: 누가 비용을 부담하고 수입과 보상을 얻는가
              |
              v
[6 Circle과 Arc의 조합]
    제품별 역할과 문제별 대응 / Arc의 처리 범위
    단계별 처리 / 예외 처리 / 대사
              |
              v
[8 종합 판단]
    어디까지 판단할 수 있고, 무엇을 더 확인해야 하는가


Arc의 직접 처리 범위
    자산 이전 / 컨트랙트 실행 / 체인 기록 확정

제품, 기관과 앱에서 처리하거나 확인할 업무
    기관 심사 / 현지 지급 / 실제 수취 확인
    계약상 지급 의무 / 업무 기록의 대사
```

- 아래쪽의 업무는 선택한 상품과 계약에 따라 담당 주체가 달라짐
- 행사와 프로그램 소개는 위 분석 흐름과 구분한 참고 내용임

## 1. 기업 지급 결제

- 약속한 대금을 지급하기 위한 기업 업무의 진행 과정을 설명함. 이 글에서는 Arc의 사용 여부와 관계없이 완료 조건, 업무 유형, 처리 주체와 처리 단계로 나누어 살펴봄
- 이 글에서 계약은 거래 당사자의 업무상 약정을, 컨트랙트는 체인에서 실행되는 스마트 컨트랙트를 뜻함

- 1.1 완료 조건: 지급 의무, 실제 수취 자산과 업무 기록의 일치 여부
- 1.2 업무 유형: 대외 지급, 수납과 분배, 통화 교환, 조건부 거래, 법인 사이의 자금 이동
- 1.3 처리 주체: 송신인과 수취인, 금융기관, 서비스 운영자, 중재자
- 1.4 처리 단계: 자금 준비, 거래 조건, 실행 승인, 자산 이전, 수취 확인, 대사

```text
[1.2 업무 유형] 무엇을 처리하는가
    대외 지급 / 수납과 분배 / 통화 교환 / 조건부 거래 /
    법인 사이의 자금 이동
        |
        |  유형마다 끝의 상태가 다름
        v
[1.4 처리 단계] 어떤 순서로 처리하는가    <--  [1.3 처리 주체] 누가 처리하는가
    자금 준비 -> 거래 조건 -> 실행 승인            송신인과 수취인, 금융기관,
    -> 자산 이전 -> 수취 확인 -> 대사              서비스 운영자, 중재자
        |                                          (단계마다 맡는다)
        |  마지막 단계인 대사에서 대조함
        v
[1.1 완료 조건] 언제 끝났다고 판단하는가
    지급 의무, 지급 자산과 업무 기록이 서로 맞는가
```

### 1.1 완료 조건

- 기업 결제의 출발점은 거래 상대에게 약속한 지급을 이행하는 일임
- 결제가 끝났는지는 송금을 실행했는지만으로 판단하지 않고, 약속한 지급(지급 의무)과 실제로 받은 자산, 그리고 둘을 잇는 기록이 서로 맞는지로 판단함
- 기업 결제가 이 세 가지로만 이루어진다는 뜻은 아님

- **지급 의무**: 청구와 계약에 따라 지급 대상과 자산을 정함
  - 상대방, 수취 계좌나 지갑, 통화와 금액, 기한 및 완료 조건을 청구에 연결해 기록함
  - 실패 뒤 새 지급을 만들더라도 이 기준은 유지하고, 계약 변경이나 부분 반환이 있었다면 무엇이 바뀌었는지 확인함
- **지급 자산**: 수취인이 원하는 자산에 따라 지급이 끝나는 지점이 달라짐
  - 공급업체 지급과 급여에서는 받는 사람이 사용할 수 있는 돈의 도착 시점이 중요함
  - 보내는 자산, 중간 기관이 보유하는 자산, 최종 수취인이 사용할 자산을 나누어 확인함
- **업무 기록**: 청구, 승인과 자산 이동의 기록을 서로 연결함

```text
[청구 하나]
    |
    +-- [기업 시스템]
    |       송장: 지급 대상과 요구 금액
    |       내부 승인: 누가 어떤 조건의 지급을 허용했는가
    |
    +-- [상품과 기관]
    |       견적 ID: 요청한 가격과 조건
    |       지급 ID: 기관에 요청한 지급과 그 상태
    |
    +-- [체인]
    |       거래 해시: 토큰의 이동
    |
    +-- [은행과 수취인]
            은행 참조와 수취 증빙: 고객에게 도착한 결과
```

### 1.3 처리 주체

| 역할            | 맡는 일                                                                                                                                                                                                                    | 확인할 것                                                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 송신인과 수취인 | 송신인은 상대, 금액과 자산을 정해 지급을 요청하고, 수취인은 약속한 자산을 수령함                                                                                                                                             | 송장과 수취 정보, 승인을 실제 수취 증빙에 연결함. 기관 사이의 토큰 이전과 고객 수취를 구별함. 같은 사업자도 수납과 지급에서 역할이 바뀔 수 있음 |
| 금융기관        | 송신 측 금융기관(OFI, Originating Financial Institution)은 지급 요청과 실행 자금을 연결함. 수취 측 금융기관(BFI, Beneficiary Financial Institution)은 심사와 토큰 수령 뒤 현지 지급을 처리함. 외환 기관은 견적과 유동성을 제공함 | 송신 측 토큰 잔액과 수취 측 현지 지급 재원을 각각 확인함. 기업 고객과 참여 금융기관을 구별함                                                    |
| 서비스 운영자   | 기관 사이의 요청과 정보를 연결하거나, 상품에 따라 자산 보관과 거래 실행을 담당함                                                                                                                                             | 기술 제공, 보관, 실행의 범위를 상품별로 확인함. 처리를 위임해도 청구, 실제 수취, 회계 기록의 연결은 남음                                      |
| 중재자(arbiter) | 정해진 권한으로 분쟁과 반환을 판단함. Refund Protocol의 반환 권한은 지정 경로와 금액으로 한정됨                                                                                                                                  | 반환 권한이 올바른 판단을 보장하지는 않음. 보관 기간이 지난 미환불 지급은 추가 중재 승인 없이 인출할 수 있음                                |

### 1.4 처리 단계

```text
[지급 의무: 청구와 계약]
          |
          v
[자금 준비] -> [거래 조건] -> [실행 승인] -> [자산 이전] -> [수취 확인] -> [대사]
                                                 |
                                                 +-> 예상과 다르게 진행되면
                                                     [실패 판별 / 재시도 / 반환 / 분쟁]
```

| 단계      | 확인할 입력                        | 처리 뒤 확인할 결과                        |
| --------- | ---------------------------------- | ------------------------------------------ |
| 자금 준비 | 필요한 자산, 금액과 조달 경로      | 실행에 사용할 자금이 준비된 상태           |
| 거래 조건 | 지급 대상, 통화와 금액             | 가격, 수수료와 기한이 결정된 상태          |
| 실행 승인 | 고객 동의, 심사 자료와 사용 권한   | 해당 실행에 필요한 승인이 충족된 상태      |
| 자산 이전 | 사용 가능한 자금과 실행 조건       | 전송, 예치나 컨트랙트상 인도가 완료된 상태 |
| 수취 확인 | 계좌나 지갑의 수취 증빙            | 실제 받은 자산과 금액이 확인된 상태        |
| 대사      | 청구, 승인, 지급, 수취와 반환 기록 | 청구와 실제 지급 및 반환 결과의 대사 완료  |

- 이 글에서는 대사를 지급 결과와 남은 의무를 확인하는 마지막 단계로 배치함. 실제 운영에서는 처리 중에도 기록과 잔액을 대조할 수 있음
  - 실패한 시도와 반환이 섞이면 같은 청구에 여러 기록이 붙으므로, 그 기록들을 함께 대조함
- 기업의 재무와 청구 시스템, 은행 메시지는 같은 지급에 관한 서로 다른 기록을 남김. ISO 20022의 업무 영역에서는 camt가 현금 관리, pain이 지급 지시, pacs가 청산과 결제, remt가 송금 정보를 가리키며, 대사에서는 이 기록들을 같은 청구와 지급에 연결함

### 2.3 사기와 오집행

- 지급 지시 자체가 위조된 경우를 사기, 실행된 지시가 승인한 업무와 달라진 경우를 오집행으로 나누어 살펴봄
- 위조된 지시의 진위는 승인 전에 확인해야 하며, 오집행을 막으려면 승인한 업무와 실제 실행할 지시를 대조해야 함. 두 문제는 송금 속도의 개선만으로 해결되지 않으며, 자금이 나간 뒤에는 회수 가능성과 후속 절차를 별도로 확인해야 함

## 3. Arc의 선택 이유

- Arc의 선택 이유는 지급 업무에서 줄이려는 부담과 연결해서 살펴봐야 함. 이 절에서는 체인 구간의 자산 관리, 확정 대기와 기능 연결이 업무의 비용과 처리에 영향을 주는 경우를 중심으로 검토함
- 예를 들어 USDC를 반복 지급하는 기업은 Arc에서 지급과 가스비를 같은 USDC로 준비하여 별도 가스 자산의 조달과 잔액 관리를 줄일 수 있음. 받은 자산을 환전한 뒤 공급업체에 지급하는 앱은 확정된 교환 결과를 다음 지급의 입력으로 사용하고 두 처리를 같은 원장에 연결할 수 있음. 수취인이 USDC를 직접 사용하거나 여러 앱이 같은 체인 상태를 다음 처리의 기준으로 삼는 업무에서는 이러한 자산 관리와 확정 및 연결의 특징이 선택 이유가 될 수 있음
- 아래 구분과 업무 예시는 이 글의 비교 기준이며 실제 고객 수요나 개선 성과를 측정한 결과는 아님. 해외 공급업체의 현지 통화 입금이 필요한 업무에서는 지급기관과 통화 경로의 제공 여부, 외환 비용과 실제 수취까지의 시간을 함께 확인해야 함. 여러 나라에 송금 서비스를 제공할 때에도 USDC를 공통 자금으로 쓰는 효과와 Arc 자체 기능의 효과를 구분해야 함. Arc 선택 여부는 이러한 전체 조건을 기존 지급 경로 및 다른 USDC 지원 체인과 비교하여 판단해야 함

- 3.1 자산 관리: 지급과 가스비에 USDC를 함께 사용하는 효과
- 3.2 거래 확정: 확정된 공유 상태가 다음 업무의 시작 조건
- 3.3 기능 연결: 같은 체인의 자산, 컨트랙트와 지급 기능을 연결할 조건

### 3.1 자산 관리

- 지급과 거래 비용의 계산 단위를 USDC로 맞추면 지급용 자산과 가스 자산을 따로 구입하고 관리하는 작업을 줄이고, 회계와 대사를 단순화할 수 있음
- USDC로 비용을 표시하는 것과 비용 금액을 고정하는 것은 다름. 수수료 설계 문서는 사용량을 반영한 가격 조정과 EWMA(exponentially weighted moving average, 최근 사용량에 가중치를 두는 이동평균)로 단기 급등을 완화한다고 설명함. 문서의 숫자는 테스트넷 구성과 정상 부하의 설계 목표임
- 비교 질문은 사용자가 항상 가스 자산을 가져야 하는가에서, 대납을 허용하는가와 누가 비용을 내며 대납이 멈추면 어떻게 되는가로 바뀜. 이미 대납을 운영하는 앱과 대납을 허용하기 어려운 기관은 Arc의 추가 가치를 다르게 볼 수 있음
- 가스비는 전체 지급 비용의 한 항목임
- 외환 견적과 수취 수수료가 그대로인 큰 지급에서는 절감 효과가 작을 수 있지만, 외환 없이 작은 금액을 자주 지급하는 업무에서는 건별 실행 비용이 중요할 수 있음
- 에이전트가 API 사용료를 지급하는 경우에도 자동화가 필요한 이유와 Arc를 선택할 이유를 구분해야 함. 자산 관리의 부담과 실제 거래 비용이 다른 구현에 비해 어떻게 달라지는지 비교할 필요가 있음

### 3.2 거래 확정

- 결정적 최종성(deterministic finality)은 거래가 미확정(unconfirmed)이거나 확정(final)이며 중간 확정 상태가 없다는 뜻임. 합의의 안전성 조건을 전제로 하며, 모든 거래가 접수 즉시 포함되거나 컨트랙트 호출이 성공한다는 보장은 아님. 공식 문서는 합의가 블록을 확정한 뒤 추가 블록 확인을 기다리지 않고 웹훅, 데이터베이스 기록과 알림을 시작할 수 있다고 설명함
- 확정된 체인 상태로 다음 컨트랙트나 자산 거래를 시작하는 업무에서는 짧은 확정 시간이 유용할 수 있음
- 반면 고객 입금의 대기 대부분이 심사나 현지 지급에 있다면 체인 확정만 줄여도 전체 시간은 크게 달라지지 않을 수 있음
- 토큰을 받은 뒤 다음 컨트랙트를 실행하는 앱은 이전 거래를 확정된 입력으로 사용할 시점과 상태 변경 대응 방식을 비교할 필요가 있음
- 체인 확정이 수취 기관의 지급 시작 조건이 되더라도 은행 이체는 별도로 완료할 필요가 있음
- 주말에도 USDC를 이전할 수 있지만 현지 통화 보충이나 은행 지급이 평일에만 가능하면 수취 기관의 사전 자금이 필요할 수 있음
- 확정된 거래를 취소할 수 없다는 것과 자금을 반환할 수 없다는 것은 다르며, 반환은 별도 거래로 기록됨

체인 거래와 고객 입금의 경계에 대한 개념도

```text
체인 거래
  [제출] -> [포함] -> [확정]
                        |
                        | 확정을 기준으로 시작할 수 있는 업무
                        +--> [다음 컨트랙트 처리: 앱의 조건 확인]
                        |
                        +--> [현지 지급: 상품과 기관의 조건 확인]
                                    |
                                    v
                             [수취인 사용 가능 확인]

포함 여부: 검증자 가동, 통신과 운영 조건을 확인
확정 결과: 합의의 안전성 조건을 확인
고객 입금: 체인 밖의 지급과 수취 결과를 확인
```

- 확정 이후의 두 갈래는 가능한 후속 업무를 나눈 것임. 모든 거래에서 두 업무를 함께 실행한다는 뜻은 아님
- Litepaper는 한 블록 안에서 확정되는 Arc 거래를 체인 간 소각과 발행의 연결에 활용할 수 있다고 설명함. 이는 설계 논지이며, 목적지 체인의 처리와 검증까지 포함한 전체 이전 시간은 이 글에서 측정하지 않았음

### 3.3 기능 연결

- ARC 토큰 백서는 같은 업무에 속한 지급, 대출과 환전이 별도 시스템에서, 종종 몇 시간이나 며칠 간격으로 결제된다고 설명함. 이 기능들을 묶은 제품을 만들려면 각 시스템의 접근을 협의하고 따로 연동한 뒤 시스템 사이의 결과를 수동으로 조정해야 한다고도 설명함
- Arc는 대출, 거래, 결제와 자산 발행을 같은 실행 환경에 두어 자산과 컨트랙트의 상호작용을 지원하려는 공통 기반임
- 기업이 보유 자금을 다른 통화로 전환한 뒤 공급업체에 지급할 때에는 지갑 서명, 자산 교환과 이전 결과를 같은 체인 상태에 연결할 수 있음. 견적, 필요한 현지 지급과 기업 장부의 갱신은 별도로 처리해야 함. Circle과 Arc의 역할 분담은 다음 절에서, 제품별 처리 경로는 단계별 처리 절에서 설명함
- 같은 체인에 있다는 사실만으로 기능이 연결되지는 않음. 컨트랙트의 인터페이스, 호출 권한과 자산 사용 조건이 맞아야 함
- 여러 체인의 USDC를 연결하는 업무는 같은 체인 안의 기능 연결과 구분해야 함. 사용하는 상품의 지원 체인과 예치 조건을 확인해야 하며, 상품의 기능을 Arc의 독점적 기능으로 해석하지 않음
- Litepaper의 지급 모듈 로드맵은 거래에 송장 세부 사항을 붙이는 기능, 온체인 환불과 분쟁, 기업 자금의 규칙에 따른 지출을 제안함. 공식 기술 문서의 Memo는 거래에 메타데이터를 붙이는 컨트랙트이며, 송장 대사와 환불 업무 전체를 자동으로 완료하는 기능과는 구분해야 함
- 급여나 거래 조건을 공개할 수 없는 업무에서는 같은 원장에서 기능을 연결하더라도 정보 보호 요건을 충족해야 함. APS(Arc Privacy Sector, Solidity 컨트랙트의 기밀 실행 환경)는 제안된 기능이며, 공식 문서에는 아직 제공되지 않은 로드맵 기능으로 명시됨. 해당 업무에 적용할 수 있는지는 현재 제공 범위를 확인하여 판단해야 하며, 기밀성이 필요한 이유는 앞의 국제 지급의 정보 보호 항목에서 설명함

- 4.3 업무 결과: 자산 이전, 자산 교환, 지급과 수취

```text
                 [Economic OS: Circle이 백서에서 제시한 Arc의 목표]
                                     |

 백서가 말하는 Arc의 구성                           Arc를 외부와 잇는 플랫폼과 서비스
```

### 4.1 역할 분담

- 아래 그림은 회사, 네트워크, 제품, 앱의 관계임. 화살표는 출시, 제공, 기능 조합, 거래 요청이고, 지분 소유나 법률상 책임은 아님. 이 구분은 서로 다른 문서의 역할을 잇기 위해 정한 것임
- 제품을 쓴다는 사실만으로 실행 체인이 Arc로 정해지지는 않음

```text
               [회사와 관련 법인]
                |              |
                | (a)          | (b)
                v              v
         [Arc 네트워크]    [제품: 지갑, 지급 API, 개발 도구]
                ^                 |
                | (d)             | (c)
                |                 v
                +---------- [앱: Circle 앱 / 제3자 앱] --(e)--> [다른 체인, 금융기관]

(a) 출시, 소프트웨어 제공   (b) 만들어 제공   (c) 앱이 기능을 골라 조합
(d) 거래 제출, 컨트랙트 호출    (e) Arc를 거치지 않는 경로
```

- 아래 표의 한 행은 한 거래에서 구별할 참여 역할 하나임. 서로 다른 문서의 역할을 연결한 설명이며, 계약상 손실 책임을 정한 표는 아님

| 참여자                  | 처리하는 일                                       | 이 역할과 구별할 것                                 |
| ----------------------- | ------------------------------------------------- | --------------------------------------------------- |
| 사용자 또는 승인 주체   | 거래 의도와 사용 권한을 승인함                      | 컨트랙트가 의도한 대로 구현됐는지는 별도 확인 대상임            |
| 앱 및 컨트랙트 개발자   | 거래를 조립하고 컨트랙트의 업무 규칙을 구현함       | 제출 성공이 지급 성공을 뜻하지 않음                 |
| 지갑과 서명 서비스      | 승인 경로에 따라 서명을 생성함                      | 모든 지갑이 같은 주체의 승인으로 작동하지 않음      |
| RPC 제공자 및 노드      | 조회와 거래 제출을 처리함                           | 접수 응답만으로 블록 포함과 성공은 확인되지 않음    |
| 허가된 검증자           | 합의에서 제안 및 투표를 수행함                      | 자산의 준비금과 법정화폐 상환을 직접 보장하지 않음  |
| 풀 노드                 | 블록의 서명을 확인하고 거래를 로컬 EVM에서 재실행함 | 일반 노드를 운영한다고 합의 투표 권한을 얻지는 않음 |
| 자산 발행자 및 금융기관 | 상품의 발행 및 상환, 고객 심사와 지급을 처리함      | 그 역할을 체인의 블록 확정으로 대체할 수 없음       |

### 4.2 거래 처리

- 아래 도식은 체인 밖의 승인과 제출, 체인 위의 실행 및 확정, 앱의 결과 조회를 요약함. 가운데의 실행 검사와 합의 투표는 관련 작업을 묶어 표시한 것이며, 구현 순서를 고정한 것은 아님

```text
 체인 밖                               |  Arc 체인 위
                                       |
 [사용자 또는 승인 주체]               |
         | (1) 의도와 권한             |
         v                             |
 [앱, 지갑: 서명]                      |
         | (2) 서명한 거래 제출 -------+--> [RPC와 노드: 접수 검사]
         |                             |               | (3)
         |                             |               v
         |                             |      [실행 검사, 합의 투표]
         |                             |               | (4)
         |                             |               v
         |                             |      [확정된 블록과 상태]
         |                             |               |
         v                             |               |
 [앱: 결과 확인] <--(5) 영수증, 성공 여부, 잔액 조회---+
```

- **승인과 제출**: 앱과 지갑이 승인된 의도로 거래를 구성하고 서명하여 제출함. 요청 인증, 자산 사용 승인과 제출 접수는 실행 성공 및 확정과 구별해야 함

---

- **실행과 확정**: 실행은 잔액과 컨트랙트 상태의 변경을 계산하고 합의는 블록을 확정함. 실행에 실패한 거래도 실패 결과로 확정될 수 있음. 아래 표의 확정 전 결과는 후보에서 실행한 경우를 뜻하며, 아직 실행하지 않은 대기 거래나 제출 시 거절된 거래와는 구별해야 함. 정본은 노드가 공식 체인 기록으로 따르는 체인을 뜻함

```text
              | 확정 전: 후보 실행 결과                        | 확정 후: 정본 기록
 -------------+------------------------------------------------+-----------------------------------------------
 실행 성공    | 상태 변경 계산, 정본 반영은 미확정             | 실행 규칙에 따른 상태 변경이 기록됨
 실행 실패    | 호출 내부 변경 되돌림, 정본 반영은 미확정      | 실패 결과와 가스비 및 논스 처리가 기록됨

 확정은 정본 기록에 관한 질문이고, 성공은 실행 결과에 관한 질문임
 실행 실패 시 호출 내부 변경은 되돌려도 사용한 가스비와 소비된 논스는 남음
```

---

- **결과 확인**: 앱은 접수, 대기, 실행 실패와 성공을 구별하고 영수증의 블록 번호와 실행 상태 및 기대한 잔액을 확인함. 체인 간 이전과 금융기관 지급의 완료는 별도로 확인해야 함

### 4.3 업무 결과

- 자산 이전, 자산 교환과 지급 및 수취는 서로 다른 완료 조건을 가지며, 모든 업무가 이들을 순서대로 거치는 것은 아님

| 업무        | 사용자가 원하는 결과                 | 완료로 보면 안 되는 처리                                       | 최종적으로 확인할 것                            |
| ----------- | ------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------- |
| 자산 이전   | 목적지에서 자산을 사용할 수 있음     | 출발지 처리가 끝나도 증명, 전달이나 목적지 처리가 남을 수 있음 | 목적지의 사용 가능한 잔액을 확인                |
| 자산 교환   | 조건에 따라 서로 다른 자산이 교환됨  | 견적과 수락만으로 실제 결제가 끝나지는 않음                    | 교환 조건과 양쪽 자산이 인도된 결과를 확인      |
| 지급과 수취 | 약속한 자산이나 통화를 수취인이 수령 | 결제 거래 완료와 기관 지급 및 실제 수령은 구별할 필요가 있음   | 해당 상품이 약속한 지급 결과와 수령 상태를 확인 |

## 5. Arc

- 앞에서 살펴본 Circle과 Arc의 연결을 바탕으로, 거래를 처리하는 프로토콜과 이용 비용 및 가치 배분의 구조를 설명함
- 프로토콜에서는 누가 거래를 실행하고 기록을 확정하는지, 경제 구조에서는 그 과정의 비용과 수익이 누구에게 연결되는지 구분함

### 5.1 Arc 프로토콜

- Arc는 여러 앱이 거래 실행과 기록 확정에 함께 사용하는 기반이며, 앱별 업무 규칙과 법률상 책임은 각 앱과 운영 주체의 영역임
- 앱이 거래를 제출하면 실행 계층이 잔액과 컨트랙트 상태의 변경을 계산하고, 합의 계층이 블록을 확정하는 구조임
- 아래 첫 도식은 환전 앱과 지급 앱이 공유하는 상태, 두 번째는 참여 주체의 권한, 세 번째는 노드 내부의 합의와 실행 연결을 설명함
- 자세한 설명: [Arc 프로토콜: 거래 처리의 구조와 동작 및 신뢰 조건은 무엇인가](arc-section-03-protocol.md)

설명용 예시: 기업이 USDC를 EURC로 환전한 뒤 공급업체에 EURC를 지급
- 두 자산과 환전 컨트랙트를 이용할 수 있고, 필요한 유동성과 사용 권한이 갖춰졌다고 가정함
- 환전과 지급은 별개의 거래이며, 지급 앱은 환전의 확정과 성공 및 실제 EURC 잔액을 확인한 뒤 다음 거래를 준비함
- 아래 잔액 변화는 교환과 지급 원금을 표시한 것임. 두 거래의 USDC 가스비는 별도로 부담하며, 대납 여부에 따라 직접 지불자가 달라짐

```text
 [환전 앱]                              [지급 앱]
  교환 조건 확인과 거래 요청             공급업체와 지급액 확인, 거래 요청
    |              ^                       |              ^
    | 거래 제출    | 결과 조회             | 거래 제출    | 결과 조회
    v              |                       v              |
 ======================== 두 앱이 공유하는 Arc ========================

  [실행 계층]
   거래를 선택하고 실행하여 블록 후보와 상태 변경을 계산
   받은 블록 후보가 실행 규칙에 맞는지도 검사
          |                              ^
          | 후보 데이터와 검사 결과      | 후보 구성과 검사 요청
          v                              |
  [합의 계층]
   블록 후보를 제안하고, 검사 결과를 반영해 검증자들이 투표
   필요한 투표권이 모이면 블록을 확정
          |
          | 확정한 블록을 실행 계층에 전달
          v
  [실행 계층]
   확정한 블록을 정본 체인에 반영하고 상태와 영수증을 보관
          |
          v
  [공통된 원장 상태: 계정 잔액, 컨트랙트 저장값과 거래 결과]

   환전 거래 성공과 확정
     기업 USDC 감소, 기업 EURC 증가
          |
          | 지급 앱이 확정된 잔액과 실행 결과를 조회
          v
   지급 거래 성공과 확정
     기업 EURC 감소, 공급업체 EURC 증가
```

- 위아래의 실행 계층은 같은 계층의 서로 다른 작업을 나타냄
- 후보를 만드는 제안자와 받은 후보를 검사하는 검증자의 작업을 함께 표시한 개념도이며, 모든 노드가 같은 순서로 수행한다는 뜻은 아님
- 실행 결과의 계산과 검사, 합의의 확정 결정, 확정된 상태의 반영이 연결되는 구조임

- 두 앱은 서로 다른 화면과 업무 규칙을 갖지만, 기업의 EURC 잔액은 Arc에 기록된 같은 잔액임
- 같은 원장을 사용해도 환전 결과의 확인, 공급업체 주소와 지급액의 검토 및 실행 승인은 앱에서 처리할 필요가 있음

---

- 사용자는 거래 내용을 승인하고 지갑으로 서명하며, RPC 제공자는 제출과 조회를 연결하고, 허가된 검증자가 후보 제안과 투표로 블록을 확정함
- 공개 풀 노드의 서명 검사와 거래 재실행은 합의 투표와 구별해야 함
- 검증자의 등록, 활성 상태와 투표권은 관리 컨트랙트의 권한을 가진 주소를 통해 변경함. 백서에서 Circle이 정하는 초기 검증자 구성과 실제 배포된 권한 주소의 보관 및 서명 주체는 구별할 필요가 있으며, 확인한 범위는 네트워크 운영 참여자에 관한 절에서 설명함

```text
 [사용자와 지갑]                         승인: 서명할 거래의 내용
     |                  ^
     | 서명한 거래      | 영수증과 잔액 조회
     v                  |
 [RPC 제공자]                            거래 제출과 조회를 연결
     |
     | 거래 전달
     v
 +==================== 허가된 검증자 집합 ====================+
 |                                                            |
 |  [검증자 노드 하나]                                        |
 |                                                            |
 |   실행 계층                                                |
 |     거래 보관, 후보 구성과 실행 검사, 확정 상태 반영       |
 |        ^                                                   |
 |        | Engine API: 요청과 결과                           |
 |        v                                                   |
 |   합의 계층 <---- 제안과 투표 ----> 다른 검증자의 합의 계층|
 |     후보 제안과 투표, 블록 확정                            |
 |                                                            |
 +============================================================+
       ^                              |
       | 검증자 등록,                 | 확정 블록과 서명
       | 활성 상태와 투표권 변경      v
 [관리 컨트랙트의 권한 보유자]   [공개 풀 노드]
                                  블록 서명 검사
                                  실행 계층에서 거래 재실행
                                  상태와 영수증 보관 및 조회
                                  합의 투표에는 참여하지 않음
```

- 검증자 노드는 실행 계층의 검사와 합의 계층의 투표를 연결해 블록을 확정함
- 공개 풀 노드는 확정된 기록과 실행 결과를 검증하며, 검증자 집합의 확정 결정에 투표하지 않음
- 앱의 결과 조회는 RPC 제공자가 연결한 노드의 상태와 영수증을 읽는 경로임

---

- 검증자 노드 내부는 합의 계층과 실행 계층으로 나눔
  - **합의 계층(Malachite)**: 검증자들이 블록 후보를 제안하고 투표하여 블록을 확정함
  - **실행 계층(Reth 기반)**: 대기 거래를 보관하고 EVM으로 거래와 컨트랙트를 실행하여 상태 변경을 계산함. EVM은 컨트랙트 코드를 실행하는 가상 머신임
- 두 계층은 Engine API로 후보 구성, 후보 검사와 확정 상태 반영을 연결함
- 앱의 제출 및 조회, 노드 내부의 계층 연결, 노드 사이의 거래 전파와 합의 통신은 서로 다른 경로임

```text
[앱과 지갑]
     |
     | JSON-RPC: 거래 제출과 결과 조회
     v
[Arc 검증자 노드의 실행 계층: Reth 기반]
     대기 거래 보관, EVM 실행, 상태와 영수증 보관
     |
     +-- devp2p --> 다른 노드의 실행 계층: 거래 전파
     ^
     | Engine API
     | 후보 구성 요청과 결과 / 후보 검사 / 확정 상태 반영
     v
[같은 노드의 합의 계층: Malachite]
     블록 후보의 제안과 투표, 확정 결정
     |
     +-- libp2p --> 다른 검증자의 합의 계층: 제안과 투표
```

- 아래 표는 환전 거래가 담긴 블록을 처리할 때 계층 사이에서 연결되는 작업을 구별한 것임. 모든 노드에서 같은 순서로 실행하는 하나의 호출 목록은 아님

| 작업           | 합의 계층과 실행 계층의 연결                                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 후보 구성      | 해당 라운드의 제안자 노드가 실행 계층에 후보 구성을 요청함. 실행 계층은 거래를 선택하고 환전 컨트랙트 등을 실행하여 블록 후보 데이터를 구성함 |
| 후보 검사      | 제안을 받은 검증자가 후보를 검사하며, 실행 계층의 유효성 판정을 합의 처리에 사용함                                                          |
| 확정 상태 반영 | 합의가 블록을 확정한 뒤, 선택한 블록을 정본 체인의 상태로 반영함. 정본은 노드가 공식 체인 기록으로 따르는 블록의 연결임                       |

- 후보를 구성하고 검사하는 과정에도 실행이 필요하므로, 실행을 확정 뒤에 처음 수행하는 작업으로 이해하면 안 됨
- 후보를 계산한 것, 유효하다고 판정한 것, 합의로 확정한 것은 서로 다른 결과임
- 앱은 확정된 거래의 영수증과 실제 잔액을 확인함. 환전 호출이 실패한 결과도 블록에 확정될 수 있으므로, 확정만 보고 공급업체 지급을 시작하지 않음
- 합의의 안전성 및 진행 조건과 노드의 스냅샷 시작 조건은 [Arc 프로토콜 상세 문서](arc-section-03-protocol.md)에서 설명함

---

- 처리 결과를 앱에서 읽으려면 Arc의 USDC 잔액 표현을 이해할 필요가 있음
- 네이티브 인터페이스와 ERC-20 인터페이스는 같은 기초 잔액을 읽는 두 방식이며, 별개의 USDC 자산은 아님
- 가스비 계산에는 18자리, 앱의 ERC-20 이전과 승인에는 6자리 정밀도를 사용하므로 단위를 구분할 필요가 있음

| 기준                     | 네이티브 인터페이스                        | ERC-20 인터페이스                                                                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 무엇인가                 | 체인이 계정에 직접 기록하는 기본 잔액      | 토큰 컨트랙트가 따르는 공통 함수 표준                                                      |
| 다른 EVM 체인에서의 USDC | ETH 등 기본 잔액과 별개                    | USDC 토큰 컨트랙트의 저장값                                                                |
| Arc에서의 USDC           | 계정의 기초 잔액                           | 같은 기초 잔액을 `0x3600000000000000000000000000000000000000`에서 조회                     |
| 소수 자릿수              | 18                                         | 6                                                                                          |
| 주된 용도                | 가스비 회계, 네이티브 송금, `msg.value`    | 앱의 이전, 사용 한도 승인과 조회                                                           |
| 잔액 조회                | `addr.balance`, `eth_getBalance`           | `USDC.balanceOf(addr)`                                                                     |
| 사용 한도 승인           | 해당 기능 없음                             | `approve`, `allowance`                                                                     |
| 이전 로그                | 시스템 발생 주소의 `Transfer`, 소수 18자리 | 시스템 `Transfer`와 ERC-20 컨트랙트의 `Transfer`를 함께 기록<br>컨트랙트 로그는 소수 6자리 |
| 표시하는 잔액            | 전체 자릿수                                | 10^-6 USDC보다 작은 부분을 제외한 잔액                                                            |

- 두 조회값을 서로 다른 자산처럼 합산하면 같은 잔액을 중복 계산하게 됨
- 출처: [Stablecoin native model](https://docs.arc.io/arc/concepts/stablecoin-native-model), [USDC system events](https://docs.arc.io/arc/references/usdc-system-events)


### 5.2 Arc Economics

- Arc를 운영하고 이용하는 데 필요한 경제적 조건을 살펴봄
- 먼저 경제 구조의 필요성과 설계 목표를 설명하고, 이용 비용, 네트워크 손익, 사업 수익, ARC 토큰 수요와 가치 귀속을 차례로 살펴봄
- 발행과 유통 및 참가자 권리의 상세: [Arc의 경제 구조: 이용 비용, 사업 수익과 참여자의 권리는 어떻게 연결되는가](arc-section-06-value-token.md)

#### 5.2.1 경제 구조: 참여 역할과 설계 목표

- Arc에 기록된 자산을 사용하고 거래와 컨트랙트를 처리하며 결과를 확인하려면, 네트워크 운영과 서비스 제공이 지속되어야 함
- 이를 위해 필요한 기능을 제공하는 기술뿐 아니라, 이용할 이유와 비용을 부담할 수 있는 조건, 운영과 서비스 제공을 지속할 재원 및 올바르게 행동할 유인이 필요함. 경제 구조는 이 조건들을 어떻게 연결할지 다룸

현재 운영 구조

```text
          [앱 사업자와 직접 거래하는 주체]
                         (USDC)
                 |                  ^
                 | 거래 제출,       | 거래 처리와
                 | USDC 가스비 지불 | 확정 결과 제공
                 v                  |
 +------------------------------------------------------------+
 | Arc 네트워크                                               |
 |                                                            |
 | 거래 실행과 확정, USDC 수수료 처리                         |
 | 운영과 이용을 지속할 비용, 재원과 수입의 귀속              |
 |                                                            | -- USDC 수수료 적립 --> [블록 수혜자]
 +------------------------------------------------------------+
          ^                                  ^
          | 실행과 합의 수행                 | USDC와 관련
          |                                  | 서비스 제공
 [네트워크 운영 참여자]                    [Circle]
                                            (USDC)
```

- 기본 수수료와 우선순위 수수료는 블록 수혜자(block beneficiary)에 적립됨. 블록 수혜자가 어느 운영 주체인지, 운영 참여자 사이의 배분 조건이 무엇인지는 별도로 확인할 필요가 있음
- 출처: [Arc 수수료 적립 규칙](https://docs.arc.io/arc/concepts/stable-fee-design)

ARC 토큰 기능이 구현될 경우의 구조

```text
          [앱 사업자와 직접 거래하는 주체]
          (USDC / ARC 토큰: 제안된 이용 혜택)
                 |                  ^
                 | 거래 제출,       | 거래 처리와 확정 결과,
                 | USDC 가스비 지불 | 자격 충족 시 ARC 토큰 이용 혜택
                 v                  |
 +------------------------------------------------------------------------------------------------+
 | Arc 네트워크                                                                                   |
 |                                                                                                |
 | 거래 실행과 확정, USDC 수수료 처리                                                             |
 | 제안: 프로토콜 수수료의 ARC 토큰 전환, 보상과 소각                                             |
 +------------------------------------------------------------------------------------------------+
    ^                 |                 ^                 |                    ^
    | 실행과 합의     | ARC 토큰        | 스테이킹으로    | ARC 토큰           | USDC와 관련
    | 수행            | 보상            | 보안 참여       | 보상               | 서비스 제공
    |                 v                 |                 v                    |
 [네트워크 운영 참여자]              [ARC 토큰 스테이커]                 [Circle]
 (ARC 토큰: 제안된 보상)             (ARC 토큰: 스테이킹과 보상)         (USDC)
```

- 두 그림은 이 글에서 참여 역할과 토큰의 관계를 비교하기 위한 개념도이며, 화살표는 제출, 기능 제공과 토큰 관련 관계의 방향을 표시함. 실제 자금 전달 경로와 수수료 수령 주체의 상세는 이후 절에서 설명함
- 현재 구조의 USDC 가스비와 백서가 제안한 ARC 토큰 기능을 구분함. ARC 토큰의 초기 발행이 이루어지더라도 이용 혜택, 스테이킹, 보상과 소각이 실제 활성화되었다는 뜻은 아님. 두 번째 그림의 ARC 토큰 관련 관계는 해당 기능이 구현되고 활성화될 경우에 적용됨
- 두 번째 그림에서 네트워크 운영 참여자는 검증자 노드의 실행과 합의 수행을, ARC 토큰 스테이커는 토큰을 통한 보안 참여를 담당하는 별도 역할로 표시함. 같은 주체가 두 활동을 함께 할 수 있지만, 스테이킹만으로 노드 운영을 수행하는 것은 아님
- 백서는 ARC 토큰 기능이 추가되더라도 가스비를 USDC로 지불하는 구성을 유지하도록 제안함. 그림에서 ARC 토큰은 별도의 경제 주체가 아니라 각 참여 역할의 보유, 사용과 참여에 연결되는 토큰으로 표시함
- 아래 항목은 이 글에서 경제 구조를 이해하기 위해 정한 기준임

| 참여 역할                      | 살펴볼 경제적 조건                                                      |
| ------------------------------ | ----------------------------------------------------------------------- |
| 앱 사업자와 직접 거래하는 주체 | 필요한 기능, 이용 비용과 비용 대비 효용, 앱 사업자의 고객 수요와 사업성 |
| 네트워크 운영 참여자           | 운영 비용, 수입과 보상 조건, 올바른 처리의 유인                         |
| Circle                         | USDC와 관련 서비스 제공의 비용, 수익과 위험                             |

- 설계 목표는 필요한 기능을 이용할 때 비용을 감당하고 예측할 수 있게 하고, 운영과 서비스 제공을 지속할 재원을 확보하며, 거래를 올바르게 처리할 경제적 유인을 마련하는 것임
- 이용 비용을 낮추는 목표와 운영 및 서비스 제공에 필요한 재원을 확보하는 목표는 상충할 수 있으므로 함께 고려해야 함
- 참여 증감의 판단 기준은 다른 선택지와 비교한 비용 대비 효용, 예상 수입과 부담할 위험임. 이 조건의 개선은 유입과 참여 확대의 유인이 되고, 악화는 이탈과 참여 축소의 유인이 될 수 있음
- 현재 USDC 수수료의 귀속과 ARC 토큰 백서가 제안한 보상 재원을 구분해야 함. 수수료를 통한 보상은 이용자의 비용 부담과 연결되고, 신규 ARC 토큰 발행을 통한 보상은 토큰 공급 증가와 연결되며 해당 기능의 활성화 여부를 확인할 필요가 있음
- 이후 절에서는 각 역할의 경제적 조건과 그 연결을 설명함. 이 조건들이 개선되면 참여할 이유가 생길 수 있지만, 현재 설계가 목표를 얼마나 충족하는지는 실제 비용, 수입과 이용 자료를 바탕으로 별도로 평가해야 함
- 먼저 이용자가 서비스를 선택하고 사용할 때 부담하는 비용부터 살펴봄

#### 5.2.2 앱 사업자와 직접 거래하는 주체: 이용 비용과 선택 조건

- 앱 사업자는 고객의 거래를 처리하기 위해 Arc를 이용하고, 직접 거래하는 개인이나 기업은 자산 이전과 컨트랙트 실행 등 자신의 목적을 위해 이용함
- 이 글에서 두 주체의 선택을 살펴보는 기준은 필요한 기능을 제공하는지, 총비용을 감당하고 예측할 수 있는지, 다른 선택지와 비교해 이용할 이유가 있는지임
- 앱 사업자는 거래 처리 비용을 직접 부담할지 고객에게 청구할지도 결정해야 함. 여기서는 이용에 따른 비용 부담을 살펴보고, 고객 수요와 전체 사업 수익성은 뒤의 Circle과 앱 사업자에 관한 절에서 설명함

기능과 비용 부담의 관계

```text
                    [Arc 이용으로 얻는 기능]
                    자산 이전과 컨트랙트 실행
                         /            \
                        v              v
              [앱 사업자]          [직접 거래하는 주체]
              고객의 거래 처리     자신의 거래 처리
                    |                     |
                    +----------+----------+
                               |
                    [부담할 비용의 구성]
                    체인 가스비 + 서비스 요금
                    포함된 가스는 중복 합산 방지

 앱 사업자: 고객에게 서비스를 제공하고, 계약에 따라 요금 청구
 직접 거래하는 주체: 자신의 거래 비용을 부담

 [필요한 기능에서 얻는 효용] <--- 비교 ---> [최종 부담할 총비용]
          |                                크기와 예측 가능성
          +-------------------+-------------------+
                              |
                  [다른 선택지와 비교한 이용 판단]
                  유지, 확대 또는 축소
```

- 위 그림은 이 글에서 기능 제공과 비용 부담 및 선택 기준을 정리한 개념도임. 기능 제공은 화살표로, 두 주체가 살펴볼 비용의 구성은 연결선으로 표시함. 앱의 고객 요금은 계약에 따라 정해지며, 앱 사업자의 비용이 모두 고객에게 전가된다는 의미는 아님. 아래에서는 가스비의 직접 지불과 최종 부담을 구분함

**어떤 비용을 누가 부담하는가**

- 이 절의 총비용은 체인 가스비와 선택한 상품의 서비스 요금을 합친 이용 비용임. 앱 사업자의 개발과 운영 등 사업 전체 비용은 뒤의 사업 수익과 지속 조건에 관한 절에서 설명함
- 수취인에게 전달할 이전 원금은 이용 비용과 구분하여 별도로 준비할 자산임
- 대납은 체인에 직접 가스비를 지불하는 주체를 바꾸는 방식임. 직접 지불자와 상품 계약상 최종 비용 부담자를 구분할 필요가 있음

| 이용 비용   | 직접 지불하거나 청구받는 주체 | 금액과 수령 대상을 확인할 근거                     |
| ----------- | ----------------------------- | -------------------------------------------------- |
| 체인 가스비 | 거래 송신자 또는 대납자       | 거래 영수증의 사용량과 단가, 적립 규칙과 수령 주소 |
| 서비스 요금 | 상품 계약의 청구 대상         | 가격표, 계약과 청구서, 상품의 청구 주체            |

- 가스비가 상품 요금에 포함되는 것은 비용의 종류가 아닌 청구 방식에 관한 구분임. 포함 항목과 정산 내역을 확인해 같은 가스비를 두 번 합산하지 않아야 함
- 이전 원금은 이전 요청, 실제 이전액과 수취인 기록으로 확인하고, 가스비 및 서비스 요금과 구분해서 기록함

직접 지불과 앱 사업자 대납의 비교

```text
 [직접 지불하는 경우]                  [앱 사업자가 대납하는 경우]

 [직접 거래하는 주체]                  [앱 사업자]
          |                                |
          | USDC 가스비 지불               | 고객 거래의 USDC 가스비 지불
          v                                v
 [Arc의 수수료 처리]                   [Arc의 수수료 처리]

 직접 지불자: 거래 주체                직접 지불자: 앱 사업자
 가스비 부담: 거래 주체                최종 부담: 고객 청구 조건에 따라 구분
                                           |
                              +------------+------------+
                              |                         |
                         별도 회수하지 않음        요금으로 회수
                              |                         |
                              v                         v
                       [앱 사업자 부담]          [회수한 부분은 고객 부담]
                                                 나머지는 앱 사업자 부담

 서비스 요금: 해당 상품의 계약에 따라 별도로 확인
 가스 포함 요금: 체인 지급액과 청구액을 같은 비용으로 두 번 합산하지 않음
 이전 원금: 수취인에게 전달할 자산이며 이용 비용과 구분
```

- 가스비 지급 화살표는 USDC 지불을, 대납 아래의 분기는 계약에 따른 비용 부담을 표시함. 대납자는 앱 사업자 외의 주체일 수도 있으나, 이 그림은 앱 사업자가 대납하는 경우와 거래 주체가 직접 지불하는 경우를 비교함

**예상 비용과 실제 비용을 어떻게 확인하는가**

| 구분              | 확인할 내용                                                                                   | 판단에 쓰는 방법                                  |
| ----------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 거래 전 예상 비용 | 예상 가스비와 계약상 서비스 요금, 가스비 포함 여부, 안내 금액이 예상치인지 최대 비용 한도인지 | 거래할지, 대납할지, 고객에게 얼마를 안내할지 판단 |
| 거래 후 실제 비용 | 영수증의 실제 가스비와 서비스 청구액                                                          | 예상과의 차이 및 최종 부담액 확인                 |

- 실제 가스비는 다음 식으로 계산함. `gasUsed`는 사용한 가스량, `effectiveGasPrice`는 가스당 실제 단가이며, 가스당 단가의 최소 단위인 10^-18 USDC를 적용해 USDC 표시 금액으로 환산함

```text
실제 USDC 가스비 = gasUsed * effectiveGasPrice / 10^18
```

- 서비스 요금은 가스비 포함 여부를 확인한 뒤 합산함. 예상 비용과 실제 비용의 차이 및 변동 가능성을 확인해 이후 비용 안내와 이용 판단에 반영함

**어떤 조건에서 이용을 선택하고 유지하는가**

- 앱 사업자는 앞에서 확인한 거래 비용을 바탕으로 직접 부담하거나 대납할 금액과 고객에게 청구할 조건을 비교함
- 직접 거래하는 주체는 필요한 기능에서 얻는 효용과 가스비 및 서비스 요금을 포함한 총비용을 다른 선택지와 비교함
- 두 주체 모두 비용 대비 효용과 비용의 예측 가능성이 개선되면 이용을 확대할 이유가 생길 수 있고, 조건이 악화되거나 더 나은 대안이 생기면 이용을 줄일 이유가 생길 수 있음. 이는 이 글의 판단 기준이며 실제 이용 변화를 측정한 결과는 아님
- 이용자가 지불한 USDC 가스비의 귀속은 다음 네트워크 운영 참여자에 관한 절에서 설명함
- 출처: [Display transaction fees](https://docs.arc.io/integrate/wallets/fee-display), [Relayers and paymasters](https://docs.arc.io/integrate/relayers-and-paymasters)

#### 5.2.3 네트워크 운영 참여자: 운영 수입과 비용, 참여 조건

- 네트워크 운영에는 비용이 들며, 참여를 지속할 경제적 조건을 살펴보려면 각 운영 주체가 얻는 수입과 사업상 효용을 운영 비용 및 위험과 비교해야 함
- 이 절에서는 합의에 참여하는 검증자를 중심으로 설명함. 공개 풀 노드의 블록 검증과 거래 재실행은 합의 투표와 다른 역할이므로, 노드를 운영한다는 사실만으로 같은 권한과 수입을 갖는 것은 아님

운영 역할과 경제적 조건의 관계

```text
                      [검증자 운영 기관]
                      블록 제안과 합의 투표
                         /           \
                        /             \
                       v               v
             [수입과 사업상 효용]   [운영 의무와 부담]
             실제로 받는 보상       보안, 가용성과 규제 준수
             자기 사업에 얻는 효용   장비, 인프라와 인력 비용
                                    의무 이행 비용과 위험
                       |               |
                       +--- 비교 ------+
                              |
                 [다른 선택지와 비교한 참여 의향]
                 새로운 기관의 참여, 기존 기관의 지속
                              |
                              | 의향과 실제 가능성을 함께 고려
                              v
                    [참여 시작과 지속의 판단]
                              ^
                              | 허용 범위와 이행할 조건
                   [참여 승인, 관리 규칙과 계약]
```

- 위 그림은 이 글에서 검증자 운영의 역할, 경제적 조건과 참여 판단을 정리한 개념도임. 위쪽 분기는 운영 기관이 살펴볼 이익과 부담을 나타내며 자산 이전을 뜻하지 않음. 운영 의무는 올바른 처리를 유도하면서 비용과 위험에도 연결됨. 경제적으로 참여할 이유가 있더라도 실제 참여와 중단은 승인, 관리 규칙과 계약의 영향을 받음. 아래에서는 현재 수수료의 귀속과 향후 ARC 토큰 보상 제안을 구분함

**어떤 자격과 역할로 참여하는가**

- 현재 기술 문서의 Arc는 허가된 검증자가 블록 후보를 제안하고 투표하는 PoA(Proof-of-Authority) 방식을 사용함. 일반 노드를 운영하거나 ARC 토큰을 보유하는 것만으로 합의 참여 자격을 얻지는 못함
- ARC 토큰 백서의 초기 거버넌스 구상에서는 Circle이 검증자 구성을 결정함. 컨트랙트에서는 권한을 가진 주소가 검증자의 등록, 활성화, 제거와 투표권 변경을 수행함. 다만 현재 배포된 권한 주소를 실제로 누가 보관하고 서명하는지까지 확인한 것은 아님. 주소별 권한은 [Arc 검증자 참여 구조](arc-section-03-protocol.md)에서 설명함
- ARC 토큰 백서는 향후 스테이킹을 통한 네트워크 보안 참여와 보상도 제안함. 검증자 노드 운영은 장비와 소프트웨어를 관리하면서 블록 제안과 투표를 수행하는 일이고, 토큰 스테이킹은 보유한 토큰을 네트워크의 보안 참여 규칙에 따라 묶어 두는 방식임. 두 활동의 참여 자격과 부담은 실제로 구현되는 규칙에 따라 달라짐
- 출처: [Arc 공식 합의 문서](https://docs.arc.io/arc/concepts/consensus-layer), [ARC 토큰 백서의 초기 거버넌스와 스테이킹 구상](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/PDFs/arc_whitepaper.pdf), [검증자 관리 컨트랙트 코드](https://github.com/circlefin/arc-node/blob/main/contracts/src/validator-manager/PermissionedValidatorManager.sol)

**무엇을 부담하고 어떤 수입과 효용을 얻는가**

- 아래 표는 이 글에서 운영 참여의 경제적 조건을 검토하기 위해 나눈 항목이며, 각 행은 수입, 효용 또는 부담을 살펴볼 항목 하나를 나타냄

| 살펴볼 항목                     | 수입과 효용 또는 부담                                                                                                        | 판단에 필요한 조건                               |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 현재 USDC 수수료                | 기본 수수료와 우선순위 수수료가 블록 수혜자에게 적립됨                                                                       | 적립액을 실제로 받는 운영 주체와 참여자별 배분   |
| 사업상 효용과 자체 비용 부담    | 운영 기관이 자기 사업에 얻는 효용을 고려해 비용 일부를 자체 부담할 수도 있음                                                 | 기관별 사업 목적과 참여 근거                     |
| 운영 비용                       | 장비, 인프라와 인력 등에 지출이 발생함                                                                                       | 유지해야 할 운영 수준과 같은 기간의 수입 및 지출 |
| 제안된 ARC 토큰 스테이킹과 보상 | 백서는 프로토콜 수수료를 전환한 ARC 토큰과 신규 발행 ARC 토큰을 보상 재원으로 제안하며, 스테이킹에는 자금 부담과 위험이 따름 | 기능 활성화, 참여 자격, 지급 조건과 토큰 가격 등 |

- 현재 수수료 적립 규칙은 확인했지만, 운영 기관별 실제 수령액과 배분은 확인하지 않았음. 따라서 블록 수혜자 적립액을 개별 검증자의 수입으로 간주하지 않음
- 사업상 효용은 이 글의 검토 항목이며 실제 기관의 참여 동기를 확인한 결과는 아님. 직접 보상이 운영 비용을 충당하는 경우와 다른 사업상 효용을 위해 비용 일부를 자체 부담하는 경우를 판단하려면 기관별 수입과 참여 근거가 필요함
- 제안된 스테이킹 보상은 현재 운영 수입과 구분해야 함. 스테이킹에는 자금을 다른 곳에 사용하기 어려워지는 부담과 토큰 가격 변화 등의 위험이 따를 수 있지만, 스테이킹 원금 전액이 장비비나 인건비처럼 이미 지출한 운영 비용인 것은 아님
- 네트워크 전체 지표만으로 개별 운영 기관의 손익을 판단할 수는 없음. 네트워크 손익과 지표의 상세는 [Arc의 경제 구조 중 네트워크 손익과 지표 설명](arc-section-06-value-token.md)에서 다룸
- 출처: [Arc 수수료 적립 문서](https://docs.arc.io/arc/concepts/stable-fee-design), [ARC 토큰 백서](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/PDFs/arc_whitepaper.pdf)

현재 PoA 운영과 향후 ARC 토큰 제안의 비교

```text
 [현재 PoA 운영]                             [향후 ARC 토큰 제안]

 [허가된 검증자]                             [검증자 노드 운영 / ARC 토큰 스테이킹]
 블록 제안과 합의 투표                       서로 다른 참여 활동
 기관의 운영 의무와 책임                     구현될 자격과 규칙에 따라 참여

 [USDC 가스비]                               [프로토콜 수수료]   [신규 발행 ARC 토큰]
        |                                           |                   |
        | 기본 + 우선순위 수수료                    | ARC 토큰 전환     |
        v                                           v                   |
 [블록 수혜자 적립]                          [전환된 ARC 토큰]          |
        :                                           | 보상 배분분       |
        : 실제 귀속과 배분은 미확인                 +---------+---------+
        v                                                     |
 [운영 기관의 실제 수입]                                      v
                                             [제안된 검증자와 스테이커 보상]
                                             지급 조건에 따름

 기관별 수입과 비용이 필요                   기능 구현과 활성화가 전제
 사업상 효용과 자체 부담도 검토              스테이킹 자금 부담과 가격 위험 검토
                                             스테이킹 원금 전액이 운영 지출은 아님
                                             전환 물량 중 소각분은 보상에서 제외
```

- 왼쪽 실선은 현재 문서의 USDC 수수료 적립 규칙을, 점선은 확인하지 않은 운영 기관별 실제 귀속을 나타냄. 오른쪽 실선은 백서가 제안한 보상 재원의 구성이며 현재 지급을 뜻하지 않음. 전환된 ARC 토큰 중 보상에 배분되는 물량만 보상으로 연결하며, 소각분은 보상 재원에서 제외해 표시함. 오른쪽의 노드 운영과 스테이킹은 서로 다른 활동으로, 보상 배분과 부담은 실제 구현되는 규칙에 따라 달라짐. 두 경우 모두 네트워크 전체 지표만으로 개별 참여자의 손익을 판단할 수는 없음

**참여자가 올바르게 처리할 유인은 무엇인가**

- [Arc 공식 합의 문서](https://docs.arc.io/arc/concepts/consensus-layer)는 현재 PoA 모델이 익명의 토큰 스테이킹 대신 신원이 알려진 기관의 책임을 활용한다고 설명함. 검증자의 보안 및 가용성에 대한 SOC 2 감사 기준, 가동 시간에 관한 서비스 수준 협약(SLA), 규제 준수 의무를 운영 조건으로 제시하며, 악의적인 행동은 프로토콜 내부의 제재를 넘어 해당 기관에 손실을 초래할 수 있다고 설명함
- 따라서 공식 문서는 기관이 운영 의무를 지키고 사업상 신뢰와 규제상 책임을 유지해야 한다는 점을 올바른 처리의 유인으로 제시함. 이는 문서가 설명하는 설계 취지이며, 개별 기관에 대한 실제 효과를 측정한 결과는 아님
- 검증자 관리 컨트랙트에는 권한을 가진 주소가 검증자를 제거하거나 투표권을 변경할 수 있는 기능이 있지만, 이를 특정 위반에 자동으로 적용되는 처벌이라고 단정할 수는 없음. 실제 운영 계약의 위반 기준, 금전적 제재와 집행 사례는 이 글에서 확인하지 않았음
- 이러한 운영 의무를 이행하려면 보안 관리, 인력과 가용성 유지 등에 비용이 들므로, 참여를 지속할 경제적 조건에도 해당 부담을 반영해야 함

**어떤 조건에서 참여를 시작하거나 지속하는가**

- 이 글에서는 수입과 사업상 효용이 운영 비용, 자금 부담과 위험을 감수할 만한지를 참여의 판단 기준으로 삼음. 다른 참여 방식이나 사업적 선택지와 비교할 때에도 앞에서 설명한 운영 의무를 이행하는 비용을 포함해야 함
- 수입이나 효용이 늘거나 비용이 줄면 새로운 기관의 참여 의향이나 기존 기관의 운영 지속 의향이 높아질 수 있고, 반대의 변화나 더 나은 대안의 등장은 참여를 재고할 이유가 될 수 있음. 이는 이 글의 판단 기준이며 실제 참여 변화를 측정한 결과는 아님
- 참여 의향과 실제 참여 가능성은 구분해야 함. 현재는 허가된 검증자만 합의에 참여하므로 신규 참여에는 승인 조건이 적용되며, 기존 기관의 운영 중단 가능성도 검증자 관리 규칙과 계약 조건에 따라 달라짐
- 현재 자료로는 검증자의 참여와 관리 구조, 수수료 적립 규칙, 기관에 요구되는 운영 의무를 설명할 수 있음. 다만 기관별 실제 수입과 비용을 확인하지 않았으므로 검증자 운영이 독립적으로 수익을 내는지는 판단할 수 없음
- 다음 절에서는 Circle과 앱 사업자가 서비스를 제공하면서 어떤 경로로 수익을 얻고 사업을 지속할 수 있는지 살펴봄

#### 5.2.4 Circle과 앱 사업자: 사업 수익과 지속 조건

- 앱 사업자는 Arc와 관련 서비스를 이용하면서 비용을 부담하는 동시에, 고객에게 서비스를 제공하면서 수입을 얻는 주체임. 앞의 이용 비용 절에서 살펴본 비용 부담과 고객 청구 조건을 여기서는 사업 수익 및 지속 조건과 연결함
- Circle은 USDC와 관련 서비스를 제공하며, 준비자산에서 발생하는 수익과 유료 서비스 제공에 따른 수입을 구분해서 살펴봐야 함. 이 절에서는 두 주체의 서비스 제공과 사업 수익을 다루며, 검증자의 운영 수입과 제안된 ARC 토큰 보상은 별도로 구분함

서비스 제공, 수입과 사업 지속 조건의 관계

```text
          [고객]                                  [USDC 준비자산]
            |                                             |
            | 서비스 요금                                 | 이자와 배당
            | 계약에 따라 지급                            | 규모, 유지 기간,
            v                                             | 수익률에 따라 발생
     [앱 사업자]                                          v
     환전, 지급 등 고객 기능 제공                     [Circle]
            |                                   USDC와 관련 서비스 제공
            |                                             |
            +---- 유료 상품 이용 시 상품 요금 지급 ------>|
            |                                             |
            |<----------- 관련 서비스 제공 ---------------+
            |                                             |
            v                                             v
 +----------------------------+             +----------------------------+
 | 앱 사업자의 경제적 조건    |             | Circle의 경제적 조건       |
 |                            |             |                            |
 | 수입                       |             | 수입                       |
 | 고객 서비스 요금           |             | 유료 서비스 수입           |
 |                            |             | 준비금 수익                |
 | 비용                       |             |                            |
 | 가스비와 제품 이용료       |             | 비용                       |
 | 개발, 운영과 고객 지원     |             | 유통 파트너 및 거래 비용   |
 |                            |             | 인건비와 IT 인프라 등      |
 | 변동과 위험                |             |                            |
 | 고객 수요와 과금 수입      |             | 변동과 위험                |
 | 서비스 제공 비용           |             | 금리와 USDC 유통량         |
 |                            |             | 서비스 수입과 비용 조건    |
 +----------------------------+             +----------------------------+
                |                                         |
                +-------------------+---------------------+
                                    |
                                    | 각 주체가 자기 조건을 비교
                                    v
                   [고객이 계속 이용할 이유가 있는가]
                   [수입이 비용과 위험을 감수할 만한가]
                   [다른 사업적 선택지보다 나은가]
                                    |
                                    v
                      [사업 지속, 확대 또는 재검토]
```

- 위 그림은 이 글에서 서비스 제공, 수입 경로와 사업 지속 조건을 정리한 개념도임. 위쪽 화살표는 요금 지급, 서비스 제공과 준비금 수익의 발생을 구분하며, 앱 사업자와 Circle 사이의 상품 요금은 유료 서비스를 이용할 때 적용됨. 고객에게 제공하는 기능은 앱 사업자 아래에 표시하며, 고객 요금 전액이 Circle로 전달된다는 뜻은 아님
- 아래쪽 두 상자는 각 사업자의 수입과 부담을 나타냄. 마지막 연결은 두 회사의 손익을 합산하는 것이 아니라 각 주체가 자신의 조건으로 사업 지속 여부를 판단한다는 뜻임. 아래에서는 과금 관계, 수입 경로, 비용과 위험 및 판단 가능한 범위를 차례로 설명함

**무엇을 제공하고 누구에게 대가를 받는가**

- 앱 사업자는 고객이 필요로 하는 기능을 제공하고 계약에 따라 요금을 청구할 수 있음. 예를 들어 앞에서 다룬 환전 앱과 지급 앱은 각각 자산 교환과 공급업체 지급을 고객에게 제공하는 기능으로 삼을 수 있음. 이때 어떤 기능에 얼마를 청구하는지는 상품과 계약에 따라 달라지며, 이 예시가 특정 앱의 실제 과금 방식을 확인한 결과는 아님
- 고객이 낸 서비스 요금은 해당 서비스를 제공하고 청구하는 사업자의 수입과 연결됨. 앱 사업자가 Circle의 유료 서비스를 이용하면 그 상품 요금은 앱 사업자에게는 비용이고 Circle에는 서비스 수입과 연결되는 금액임. 다만 앱이 받은 고객 요금 전액을 Circle의 수입으로 볼 수는 없음
- 가스비를 고객에게 별도로 청구하는지, 상품 요금에 포함하는지, 앱 사업자가 자체 부담하는지는 앞에서 살펴본 계약 조건에 따름. 가스비를 회수하더라도 앱 사업자에게는 체인에 지급하는 비용이 있으므로, 회수한 금액 전부가 이익이 되는 것은 아님

**누가 어떤 경로로 수입을 얻는가**

- 아래 표는 이 글에서 사업 수익을 이해하기 위해 구분한 경로이며, 각 행은 수입이 발생하는 경로 하나를 나타냄

| 수입을 얻는 주체와 경로 | 수입이 발생하는 조건                                       | Arc 이용과 연결할 때 확인할 것                      |
| ----------------------- | ---------------------------------------------------------- | --------------------------------------------------- |
| 앱 사업자의 서비스 수입 | 고객에게 제공한 기능과 계약상 과금 조건에 따른 서비스 제공 | 고객 수요, 과금 대상과 요율, 실제 수입 및 관련 비용 |
| Circle의 서비스 수입    | 유료 상품의 계약 조건에 따른 서비스 제공                   | 이용한 제품, 과금 대상과 요율, 제공 및 청구 조건    |
| Circle의 준비금 수익    | USDC를 뒷받침하는 준비자산에서 이자와 배당이 발생함        | 전체 USDC 유통량, 평균 준비자산, 유지 기간과 수익률 |

- Circle의 준비금 수익은 고객이 Arc 거래마다 내는 서비스 요금과 다른 경로임. Arc에서 USDC가 더 많이 이전되더라도 전체 유통량이나 준비자산이 같은 비율로 늘어나는 것은 아니며, 준비금 수익은 개별 지갑의 보유 시간보다 전체 준비자산의 규모, 유지 기간과 수익률을 기준으로 살펴봐야 함
- 이전 원금은 수취인에게 전달할 자산이고, 체인 가스비는 앞에서 설명한 수수료 적립 규칙에 따름. 이를 앱 사업자나 Circle의 서비스 매출로 일괄 해석할 수는 없음
- Circle 공시는 준비금 수익과 서비스 관련 수입을 구분하고, 서비스 수익은 계약에 따른 제공 의무를 이행할 때 인식한다고 설명함. 따라서 계약, 청구나 입금이 있다는 사실만으로 같은 시점에 같은 금액의 매출이 확정된다고 볼 수는 없음
- 출처: [Circle 공시의 수익 인식 및 준비금 수익 설명](https://www.sec.gov/Archives/edgar/data/1876042/000187604226000248/crcl-20260630.htm)

**수입을 얻기 위해 어떤 비용과 위험을 부담하는가**

- 앱 사업자는 체인 가스비와 선택한 제품의 이용료뿐 아니라 개발, 운영과 고객 지원 비용도 부담함. 이 글에서는 고객 수요와 과금 수입의 변동, 서비스 제공 비용의 증가를 사업 지속에 영향을 주는 검토 항목으로 삼음. 가스비를 고객에게 회수한 부분과 자체 부담한 부분도 비용 및 수입 내역에서 함께 살펴봐야 함
- Circle 공시는 유통 파트너에게 지급하는 비용과 거래 관련 비용, 인건비, IT 인프라 비용 등을 제시함. 준비금 수익이 발생하더라도 이러한 비용을 반영하기 전의 금액을 회사의 이익으로 볼 수는 없음
- Circle은 금리 변화가 준비자산 수익률과 준비금 수익에 영향을 준다고 설명하며, USDC 유통량도 고객 행동 등에 따라 달라질 수 있다고 설명함. 따라서 Arc 이용량뿐 아니라 준비자산 수익률, 유통량과 비용 조건의 변화도 함께 살펴봐야 함
- 이 공시는 Circle 전체 사업에 관한 근거임. 회사 전체의 수입과 비용을 그대로 Arc의 수입과 비용으로 간주하지 않으며, Arc의 기여를 판단하려면 Arc에 연결되는 수입과 비용을 별도로 식별해야 함
- 출처: [Circle 공시의 비용 구조와 금리 위험 설명](https://www.sec.gov/Archives/edgar/data/1876042/000187604226000248/crcl-20260630.htm)

**어떤 조건에서 사업을 지속하거나 확대하는가**

- 이 글에서는 다른 서비스와 비교한 고객 수요, 실제 수입, 서비스 제공 비용과 위험을 사업 지속 및 확대의 판단 기준으로 삼음. 고객이 계속 이용할 이유가 있고 그 이용에서 얻는 수입이 제공 비용과 위험을 감수할 만한지 함께 살펴봐야 함
- 수요 증가, 과금 수입의 개선이나 비용 절감은 사업을 지속하거나 확대할 유인이 될 수 있고, 반대의 변화나 더 나은 대안의 등장은 사업을 축소하거나 재검토할 이유가 될 수 있음. 이는 이 글의 판단 기준이며 실제 사업 변화를 측정한 결과는 아님
- 현재 자료로는 서비스 제공과 수입이 연결되는 경로, 준비금 수익의 발생 조건과 사업상 부담을 설명할 수 있음. 다만 개별 앱의 실제 손익과 Arc에 귀속되는 Circle의 수입 및 비용을 확인하지 않았으므로, Arc 이용이 각 사업자의 수익성을 얼마나 개선했는지는 판단할 수 없음
- 다음 절에서는 이들의 사업 수익과 구분하여, 제안된 ARC 토큰 기능이 참여 동기와 가치 귀속에 어떻게 연결되는지 설명함

#### 5.2.5 ARC 토큰: 참여 동기와 가치 귀속

- 앞에서는 USDC로 거래할 때의 이용 비용, 검증자의 운영 조건과 서비스 제공자의 사업 수익을 살펴봄. ARC 토큰 백서는 여기에 이용 비용의 할인과 보조, 스테이킹을 통한 보안 참여와 보상, 경제 변수의 결정 권한을 연결하는 토큰을 추가로 제안함
- ARC 토큰은 별도의 경제 주체가 아니라 각 참여 역할이 선택할 수 있는 수단임. USDC를 주고받고 가스비를 지불하기 위해 ARC 토큰을 반드시 보유해야 하는 것은 아니며, 아래 ARC 토큰 기능은 실제 구현과 활성화가 전제됨

**USDC 가스비는 ARC 토큰 수요와 어떻게 연결되는가**

- Ethereum에서는 거래 송신자가 ETH로 가스비를 지불하므로 거래를 제출하는 쪽에서 ETH를 마련해야 함. 반면 Arc의 현재 USDC 가스비 구조에서는 거래를 위해 ARC 토큰을 마련할 필요가 없음
- ARC 토큰 백서는 받은 프로토콜 수수료를 ARC 토큰으로 전환해 보상과 소각에 배분하는 방식을 제안함. 사용자의 직접적인 가스 지급 수요 대신 프로토콜의 수수료 전환을 통한 ARC 토큰 취득 수요를 연결하려는 것임

가스비 지급 자산과 수수료 처리의 비교

```text
 [Ethereum: 현재]                [Arc: 현재 기술 문서]          [Arc: ARC 토큰 백서의 제안]

 [거래 송신자]                   [거래 송신자]                  [거래 송신자]
       |                               |                              |

 가스 소비       = 거래 처리에 사용한 계산 작업량
```

- 위 그림은 지급 자산과 수수료 처리 규칙을 비교하며, 화살표는 지급, 전환과 배분의 경로를 나타냄. 왼쪽과 가운데는 현재 기술 문서의 구조이고 오른쪽은 백서의 제안임. 소각 여부와 배분 대상은 각 네트워크의 규칙에 따라 달라짐
- 가스 소비는 계산 작업량을 사용했다는 뜻이며 토큰 소각을 뜻하지 않음. USDC를 ARC 토큰으로 교환하는 것 자체도 USDC 소각이 아니므로 지급, 교환과 공급의 영구 제거를 구분해야 함
- 이 그림은 토큰 취득이 발생하는 위치의 차이를 설명하며 동일한 가격 효과를 보장하지는 않음. ARC 토큰의 전환에 사용할 유동성과 가격 결정 방식은 실제 구현에서 확인할 필요가 있음
- 출처: [Ethereum 가스 문서](https://ethereum.org/developers/docs/gas/), [Arc 수수료 적립 규칙](https://docs.arc.io/arc/concepts/stable-fee-design), [ARC 토큰 백서의 Fee mechanics and conversion](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/PDFs/arc_whitepaper.pdf)

**각 참여자는 어떤 이유로 ARC 토큰을 보유하거나 사용하는가**

- 백서는 ARC 토큰 보유 또는 스테이킹에 따른 가스 할인과 보조, 플랫폼 서비스의 수수료 할인 및 우선 접근, 스테이킹 보상과 의사결정 참여를 제안함
- 아래 표는 이 글에서 참여 동기를 살펴보기 위해 정한 비교 기준이며, 각 행은 ARC 토큰 기능을 선택할 이유와 부담을 비교할 참여 역할 하나를 나타냄

| 참여 역할                       | 제안된 ARC 토큰 기능을 선택할 이유                             | 함께 비교할 부담과 조건                                                                   |
| ------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 앱 사업자와 직접 거래하는 주체  | 가스 및 서비스 비용의 할인과 보조, 우선 접근                   | 대상 상품과 자격, 혜택의 크기, ARC 토큰 취득 비용과 보유 중 가격 변동 및 자금 부담        |
| 네트워크 운영 참여자와 스테이커 | 네트워크 보안 참여에 따른 보상                                 | 노드 운영과 스테이킹 각각의 자격, 운영 비용과 스테이킹 자금의 부담, 위험과 실제 보상 조건 |
| 의사결정에 참여하려는 주체      | 수수료와 발행량 및 보상과 소각 비율 등 경제 변수의 결정에 참여 | 권한을 얻을 조건과 범위, 실제 결정 및 집행 절차                                           |

- 노드 운영과 토큰 스테이킹은 다른 활동이며, 의사결정 참여는 앱 사업자나 운영 참여자와 겹칠 수 있는 역할임. 따라서 표의 행들이 서로 독립된 집단을 뜻하는 것은 아님
- 이 글에서는 혜택, 기대 보상과 결정 권한이 취득 비용, 자금 부담과 위험을 감수할 만한지를 참여의 판단 기준으로 삼음. 조건이 유리해지면 참여할 이유가 될 수 있고, 반대의 변화나 더 나은 대안의 등장은 참여를 줄일 이유가 될 수 있음
- 단순 보유에 따른 이용 혜택과 보안 참여에 따른 보상은 구분해야 하며, Circle의 사업 수익이 ARC 토큰 보유자에게 자동 귀속되는 것도 아님
- 출처: [백서의 Introducing the ARC Token, ARC Utility in Depth 및 Platform-level utility 설명](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/PDFs/arc_whitepaper.pdf)

**수수료와 신규 발행은 보상 및 공급 변화에 어떻게 연결되는가**

- 이 글에서 가치 귀속은 네트워크 활동에서 발생한 수수료가 누구의 보상으로 배분되고 ARC 토큰 공급에 어떻게 반영되는지를 살펴보는 뜻으로 사용함. 모든 보유자의 수익이나 토큰 가격 상승을 뜻하는 것은 아님
- 아래 그림은 앞의 수수료 처리 비교에서 ARC 토큰 제안 부분을 확장해 신규 발행 재원까지 함께 표시함. 백서는 초기 신규 발행 보상으로 참여를 지원한 뒤 실제 활동에서 발생한 수수료 재원의 비중을 높이는 방향을 제시함

```text
 [수수료에서 마련한 ARC 토큰] ----> [검증자와 스테이커 보상]
                               두 재원을 구분해서 판단

 전체 공급 변화: 같은 기간의 신규 발행량과 소각량을 비교
```

- 화살표는 제안된 전환과 배분 경로이며 현재 지급을 뜻하지 않음. 수수료 전환은 ARC 토큰을 마련하는 경로이고, 신규 발행과 소각은 공급량을 변화시키는 경로임
- 수수료에서 마련한 보상은 실제 이용자가 낸 비용에 연결되고, 신규 발행 보상은 토큰 공급 증가에 연결됨. 따라서 보상 전부를 네트워크 이용이 만든 수익으로 해석할 수는 없으며, 이 배분이 모든 ARC 토큰 보유자에게 자동 지급되는 것도 아님
- 소각과 신규 발행이 함께 존재하므로 전체 공급의 감소 여부는 같은 기간의 발행량과 소각량을 비교해야 판단할 수 있음
- 출처: [백서의 Staking, Supply and inflation 및 Fee mechanics and conversion 설명](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/PDFs/arc_whitepaper.pdf)

**이 구조는 ARC 토큰의 필요성과 가격을 얼마나 설명하는가**

- 아래는 백서의 기능 제안을 바탕으로 한 이 글의 경제적 해석임. 참여자가 보유나 스테이킹으로 얻을 혜택이 취득 비용과 위험을 감수할 만큼 크다고 판단하면 ARC 토큰에 대가를 지불할 이유가 생김. 다만 지불할 이유가 있다는 것, 지속적으로 보유한다는 것과 특정 시장가격이 적정하다는 것은 서로 다른 판단임
- 아래 표는 가스비 지급과 할인 및 수수료 전환에 따른 취득 수요만 비교한 것으로, 각 행은 실제 변경 이력이 아닌 가상의 설계 조건을 나타냄. 마지막 행은 백서가 제안한 수요 경로에 해당하며, 스테이킹과 의사결정 등 나머지 기능은 앞의 참여 역할 표에서 다룸

| 비교할 설계                                                    | ARC 토큰을 취득할 이유                                                             |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 가스비를 ARC 토큰으로 지불                                     | 거래를 위해 지급자가 ARC 토큰을 마련해야 함                                        |
| USDC로 가스비를 지불하고 ARC 토큰에는 할인 혜택만 부여         | 예상 절감액이 취득 비용과 위험을 감수할 만하다고 판단하는 참여자가 선택적으로 취득 |
| USDC로 가스비를 지불하되 프로토콜이 수수료를 ARC 토큰으로 전환 | 할인 목적의 취득 외에 프로토콜의 수수료 전환에 따른 취득 수요도 발생               |

- 가스비를 ARC 토큰으로 내는 가상의 설계와 비교해, USDC 지급과 할인 혜택만 제공하는 설계에서는 직접적인 가스 지급 수요가 발생하지 않음. 다만 백서는 수수료 전환도 제안하므로, 가스비 지급 자산이 아니라는 이유만으로 훨씬 낮게 평가할 수는 없으며 대체하는 전환 수요와 보유 혜택의 강도를 살펴봐야 함
- 수수료 전환은 ARC 토큰을 취득하는 흐름을 만들지만, 보상 수령자는 받은 토큰을 보유하거나 매도할 수 있음. 할인과 참여 혜택은 보유할 이유가 될 수 있으며, 시장가격은 이러한 수요뿐 아니라 매도와 신규 공급의 영향도 받음. 따라서 전환 수요가 있다는 사실만으로 장기 보유나 가격 상승이 보장되지는 않음
- 가스 지급에 쓰이는 토큰도 거래 직전에 필요한 만큼만 취득해서 지불할 수 있다면 반복적인 사용과 장기 보유가 다를 수 있음. 가스비 지급 여부 하나만으로 토큰 가치가 줄어드는 비율을 정할 수는 없음
- 신규 발행으로 더 많은 ARC 토큰을 보상한다는 사실만으로 지불 의사가 설명되는 것도 아님. 토큰을 원하는 이유가 오직 더 많은 같은 토큰을 받는 것뿐이라면 설명이 반복되므로, 실제 이용에서 생기는 혜택과 수수료 재원을 함께 평가해야 함
- 별도 토큰의 필요성은 취득 수요와 구분해서 판단해야 함. 개념적으로는 USDC로 운영자에게 직접 보상하는 설계도 가능하므로, ARC 토큰을 추가해 수수료 배분, 이용 혜택, 보안 참여와 결정 권한을 연결하는 방식이 어떤 효과를 내는지가 평가 대상임
- 근거가 되는 기능 제안은 [ARC 토큰 백서의 Platform-level utility, Supply and inflation 및 Fee mechanics and conversion](https://6778953.fs1.hubspotusercontent-na1.net/hubfs/6778953/PDFs/arc_whitepaper.pdf)에 있으며, 설계 비교와 지불 의사 및 가격에 관한 평가는 이 글의 해석임

**가격을 평가하려면 어떤 수입과 귀속을 확인해야 하는가**

- 앞의 설계를 바탕으로 이 글에서 중요하게 보는 것은 지속 가능한 프로토콜 수입의 규모와 그중 ARC 토큰에 연결되는 몫임. 토큰의 용도를 추가하거나 수수료를 ARC 토큰으로 전환한다는 사실만으로 높은 가격을 설명할 수는 없음
- 수입이 지속되려면 고객이 반복해서 비용을 지불할 만큼 서비스가 유용해야 함. 유료 기능을 추가하는 것만으로는 부족하며, 고객이 다른 대안과 비교해 그 기능을 선택하고 계속 사용할 이유가 있어야 함
- 백서는 출시 시점의 수입원으로 기본 거래 수수료와 우선순위 수수료를 제시하고, 이후 MEV(Maximal Extractable Value, 거래 포함과 순서 등에서 얻을 수 있는 가치)와 관련된 블록 구성 권한 경매 수입 및 프라이버시 거래와 특화된 거래 처리 경로의 수수료를 예상함. 이는 백서가 제안한 수입원으로, 각 기능의 구현과 활성화 및 실제 수입을 확인해야 하며 미래 수입을 현재 수입에 합산하지 않음
- Arc를 통과하는 자금의 규모와 프로토콜의 수수료 수입은 다름. 큰 금액을 이전하더라도 거래당 수수료가 작으면 ARC 토큰 취득에 연결되는 재원은 작을 수 있음. Circle이나 앱 사업자의 매출도 프로토콜에 귀속되는 규칙이 있어야 ARC 토큰의 수수료 전환 재원에 포함할 수 있음
- 따라서 ARC 토큰의 취득과 소각 및 수수료 기반 보상에 얼마를 어떤 규칙으로 배분하며, 검증자 보상이 운영을 지속할 재원이 되는지 살펴봐야 함. 검증자에게 지급하는 ARC 토큰 보상 자체가 운영 재원이 될 수 있으므로, 운영비를 먼저 차감한 잔액만 ARC 토큰으로 전환한다고 해석하지 않음. 보상 수령자는 받은 토큰을 다시 매도할 수 있으므로, 전환 총액뿐 아니라 소각되는 물량과 보유할 이유를 함께 확인해야 함
- 혜택별로 적용 대상과 평가 기준을 구분해야 함. 수수료 기반 보상은 지급 자격과 배분 규칙 및 보상 대상의 스테이킹 규모에 따라 달라지고, 할인 혜택은 자격과 실제 이용량에 따라 달라짐. 소각은 토큰 공급을 변화시키는 경로이며 보유자에게 보상을 직접 지급하는 것은 아니므로, 모든 혜택을 전체 토큰 수로 나누어 평가하지 않음
- 공급 변화는 이러한 혜택과 함께 살펴봐야 함. 신규 발행은 총공급을 늘리고, 이미 발행된 물량의 유통은 시장에서 거래 가능한 공급을 늘릴 수 있음. 보상 대상의 스테이킹 규모와 시장에서 거래 가능한 물량은 서로 다른 기준이므로 각각 확인해야 함
- 이 글의 판단 질문은 "얼마나 많은 자금이 Arc를 통과하는가"보다 "얼마의 지속 가능한 수입이 ARC 토큰에 연결되며, 혜택별 대상과 규모 및 공급 변화는 어떠한가"임. 그 수입과 귀속의 규모 및 지속 가능성에 대한 기대가 높아지면 가격 상승의 경제적 근거가 될 수 있지만, 실제 가격을 평가하려면 현재 시장가격이 이미 반영한 기대도 비교해야 함

- 백서는 ARC 토큰을 취득하고 보유할 이유가 생기는 경로를 제안하지만, 그 경로의 실제 작동과 경제적 규모를 입증한 것은 아님. 설계는 변경되거나 구현되지 않을 수 있으므로 실제 제공 혜택, 보상과 결정 권한의 집행 및 전환과 발행 및 소각 내역이 판단의 근거가 되어야 함
- 이 글에서는 이러한 기능의 실제 운영 내역과 참여자별 비용을 확인하지 않았으므로 별도 토큰의 필요성이 충족되었는지, 참여자가 순이익을 얻는지, 시장가격이 적정한지를 확정할 수 없음. 각각은 기능의 효과, 혜택과 부담, 시장의 수요와 공급을 구분해서 판단해야 함

## 6. Circle과 Arc의 조합

- Circle 제품과 Arc를 한 지급에 함께 쓰는 방식을 구성 요소별 역할, 처리 범위, 정상 처리, 예외 처리와 대사로 나누어 설명함

- 6.1 제품별 역할과 문제별 대응: 제품이 맡는 업무, 2절 문제에 대한 대응
- 6.2 Arc의 처리 범위: 체인 처리와 기관 및 은행 처리의 경계
- 6.3 단계별 처리: 자금 준비, 거래 조건, 실행 승인, 자산 이전, 수취 확인
- 6.4 예외 처리: 실패 판별, 재시도, 반환, 분쟁
- 6.5 대사: 기록 연결, 금액 확인, 중복 판별, 의무 확인

- 이 절에서는 기업이 Circle 제품을 통해 Arc를 이용하는 경로를 중심으로 설명함. 제품이 바꾸는 업무 절차와 Arc가 맡는 실행 구간을 구별할 필요가 있음
- 아래 그림은 같은 업무에서 검토할 처리 경로, 상품과 자산을 함께 표시한 것임. 서로 배타적인 대안은 아니며, 관리형 상품이 기존 체인의 USDC나 토큰화 자산을 활용할 수도 있으므로 실제 조합과 지원 조건을 확인해야 함

### 6.2 Arc의 처리 범위

- Arc는 선택된 경로의 USDC 이전, 컨트랙트 실행과 체인 확인을 맡음. 현재 기술 문서의 네이티브 가스 자산은 USDC이며, 다른 자산을 받는 전용 paymaster 연동 계획과는 구분해야 함
- 공식 문서는 미확정과 최종 확정을 구별함. 체인 확정, 실행 성공과 고객 지급 완료는 각각 확인해야 하며, 가스의 표시 단위, 단가와 전체 지급 비용도 구별해야 함

- 아래는 기관을 거치는 지급의 예시이며, 기관 견적과 심사, 기업 승인, Arc 실행과 현지 지급의 경계를 표시함. 직접 토큰을 이전하는 업무는 현지 은행 지급을 거치지 않을 수 있음

```text
[기관 견적과 심사, 기업 승인]
             |
             v
[Arc의 자산 이전과 컨트랙트 실행] -> [현지 지급] -> [실제 수취]
             |
             v
[거래 증거와 실행 결과를 업무 기록에 연결]
```

### 6.3 단계별 처리

- 아래 도식은 자금 준비부터 수취 확인까지를 연결하고, 자산 이전을 제품별 경로로 나눔. 상품별 선행 조건과 세부 순서는 서로 다르며, 대사와 예외 처리는 뒤의 하위절에서 정리함

```text
[자금 준비] -> [거래 조건] -> [실행 승인] -> [자산 이전] -> [수취 확인]
                                                  |
                                                  | 자산 이전에 사용하는 경로
                                                  +-- 기관 지급
                                                  +-- 관리형 수납과 지급
                                                  +-- 기관 외환
                                                  +-- 조건부 컨트랙트
```

**자금 준비**

- 송신 기관은 보유 USDC나 선택 사항인 Mint로 지급 자금을 준비하고, 사용 가능한 잔액과 미결제 잔액, 담보 및 가스비를 구별하며, Gateway의 통합 잔액에도 예치와 지출 서명 조건이 남음


Circle Mint를 쓰는 예시
- 미결제 잔액이 사용 가능 잔액으로 바뀐 뒤 운영 지갑을 준비하는 과정을 보여 줌
- Mint는 여러 조달 경로 가운데 하나이며 선택 사항임

```text
[은행 자금]
     |  Mint 계정에 입금
     v
[Mint 계정의 Unsettled 잔액]   입금은 보이지만 아직 결제가 확인되지 않았음
     |  자금 결제 확인
     v
[Mint 계정의 Available 잔액]   바로 이전하거나 상환할 수 있음
     |  승인한 운영 지갑으로 이전
     v
[OFI 운영 지갑의 USDC]         여기까지가 자금 준비임
     :
     :  견적, 승인과 심사가 끝난 뒤
     v
[CPN 지급의 체인 전송]         기관 지급
```

**실행 승인**

- 고객의 가격 승인, 기관 심사와 지갑 서명 및 토큰 사용 권한을 따로 확인함. 실행할 견적, 주소와 체인이 승인 범위에 맞는지 대조하며, 가스 대납 조건과 Memo의 직접 호출 제한도 확인함

- 아래 도식은 기관 심사가 필요한 지급과 외환 업무에서 승인 대상을 구별한 것임. 각 업무에 적용되는 승인과 심사 조건을 충족해야 하며, 견적이나 실행 대상이 바뀌면 기존 승인의 적용 범위를 다시 확인해야 함
- 기관의 심사 항목에는 고객 신원 확인(KYC), 기업 고객 확인(KYB), 자금세탁 방지(AML), 송수신인 정보 전달 규칙(Travel Rule)과 추가 정보 요청(RFI)이 포함될 수 있음. StableFX의 EIP-712는 구조화한 데이터에 대한 서명 방식이며, Permit2는 토큰 사용 권한을 처리하는 컨트랙트임

```text
[고객의 승인]       [기관의 심사]                [지갑 서명과 토큰 사용 권한]
가격과 지급 조건    고객 자료와 지급의 적격성    실제 자산 이동
                    KYC, KYB, AML,               외환에서는 EIP-712 서명과
                    Travel Rule, RFI             Permit2 권한
  |                   |                            |
  +-------------------+---+------------------------+
                          |  해당 업무에 필요한 조건을 충족함
                          v
                     [자산 이전]


NOTE: 견적, 수취 주소, 체인이나 컨트랙트가 바뀌면 이전 승인을 그대로 쓸 수 있는지 다시 확인함
```

**자산 이전**

- 직접 전송, 관리형 발행과 소각, 외환 예치와 인도 및 조건부 인출을 구별함. Send의 같은 체인 전송, Bridge의 체인 간 이전과 묶음 호출의 개별 결과를 각각 확인함

제품별 자산 이동, 잔액과 후속 업무의 비교

```text
[자산 이전]
    |
    +-- 기관 지급 (CPN)
    |       이동: OFI의 USDC -> BFI의 USDC
    |       결과가 남는 곳: 수취 기관의 잔액
    |       이어지는 업무: BFI의 현지 지급과 은행 처리
    |
    +-- 관리형 수납과 지급 (Managed Payments)
    |       이동: 고객 USDC -> Circle 보관 -> 소각, 또는 발행 -> 등록한 수취 지갑
    |       결과가 남는 곳: 파트너 은행 계정의 법정화폐, 또는 수취 지갑의 토큰
    |       선행 조건과 후속 확인: 주소 승인과 준법 처리, 정산 및 수취 결과
    |
    +-- 기관 외환 (StableFX)
    |       이동: 담보와 추가 자금 -> FxEscrow -> 양쪽 통화의 인도
    |       결과가 남는 곳: 인도 전에는 예치 잔액, 인도 뒤에는 각 기관의 토큰
    |       이어지는 업무: 은행 자금이 필요하면 발행자 상환
    |
    +-- 조건부 컨트랙트 (Refund Protocol)
            이동: 구매자의 지급 -> 컨트랙트 -> 판매자 인출, 또는 지정 주소로 반환
            결과가 남는 곳: 인출이나 반환 전에는 컨트랙트의 예치 잔액
            조건과 후속 확인: 보관 기간, 필요한 중재 판단과 반환 주소
```

**기관 지급**

- CPN은 견적 선택과 고객 승인, 지급 생성과 수취 기관 심사 및 추가 자료 요청, 송신 기관의 USDC 전송과 수취 기관의 현지 지급을 연결함. 체인 확인과 고객 입금은 따로 추적해야 함

CPN 도식: 자금 준비, 심사, USDC 이전과 최종 지급의 순서

```text
[USDC 운영 지갑 준비]
          |
[견적 요청 -> 조건 선택 -> 고객 승인]
          |
[지급 생성 -> BFI 심사 -> 필요한 RFI 응답]
          |
[거래 서명과 제출 -> 체인 확인 -> BFI 토큰 수령]
          |
[BFI 현지 지급 -> 은행 처리 -> 수취인 계좌 반영]
```

**관리형 수납과 지급**

- Managed Payments는 수납 토큰을 보관하고 심사한 뒤 소각하여 파트너 은행에 법정화폐로 정산하고, 지급에서는 은행 자금 결제 후 토큰을 발행하여 승인된 지갑으로 보내며 주소 승인과 지역별 조건이 남음

```text
수납: [고객 USDC] -> [Circle 보관과 심사] -> [소각] -> [파트너 은행의 법정화폐]

지급: [파트너 은행 자금] -> [Circle 자금 결제 확인과 발행] -> [등록한 수취 지갑의 토큰]
```

**기관 외환**

- StableFX는 체인 밖의 견적과 서명 뒤 담보와 추가 자금을 예치하여 양쪽 통화를 인도함. 예치 중의 위험과 은행 자금으로의 상환 조건은 남으며, 선입금 순서와 상계 범위는 문서와 실제 구현을 대조할 필요가 있음

외환 도식: 최종 인도 전에 담보와 추가 자금이 예치되는 구간

```text
체인 밖: [RFQ -> 견적 -> 수락 -> 양쪽 서명]
                              |
체인 안:              [거래 등록과 담보 예치]
                              |
                 +------------+------------+
                 |                         |
         [테이커의 추가 자금]       [메이커의 추가 자금]
                 |                         |
                 +----------+--------------+
                            |
                [FxEscrow: 양쪽 통화의 최종 인도]
                            |
                            +-> [테이커가 받을 토큰]
                            +-> [메이커가 받을 토큰]
                            +-> [수수료 수령자]

은행 전환이 필요하면: [수령 토큰 -> 별도 발행자 상환 -> 은행 자금]
```

**조건부 컨트랙트**

조건부 컨트랙트 도식: 판매자 인출과 지정 주소 반환

```text
[구매자의 지급] -> [컨트랙트: 금액, 판매자, 반환 주소와 중재자]
                                 |
                 +---------------+---------------+
                 |                               |
         [조건에 맞는 판매자 인출]        [권한에 맞는 환불 판단]
                 |                               |
           [판매자 수령]                 [지정 반환 주소로 지급]
```

**수취 확인**

- 체인 확정, 실행 성공, 지급 객체 완료와 고객의 실제 수취를 구별하고 약속한 자산과 금액에 대조하며, `Payment COMPLETED`도 수취인의 사용 가능한 은행 잔액이나 기업의 회계 마감을 보장하지 않음

| 완료를 관측할 대상 | 가능한 확인                                    | 아직 같은 것으로 볼 수 없는 것     |
| ------------------ | ---------------------------------------------- | ---------------------------------- |
| 체인 거래          | 해시, 실행 결과와 체인 확인                    | BFI의 현지 지급과 고객의 실제 입금 |
| 지급 객체          | BFI가 처리한 지급 상태와 통지                  | 지급 방식에 따른 은행 반영 시각    |
| 수취인 잔액        | 실제 계좌 또는 지갑에 도착한 자산과 금액       | 기업의 송장과 계약상 의무 처리 완료  |
| 기업의 지급 의무   | 수취 사실과 계약, 송장 및 지급 기록의 대사 | 장부 마감과 증빙의 자동 완성       |
| 회계 기록          | 금액, 통화와 시각, 수수료 및 반환의 정리       | 모든 고객의 권리와 분쟁 해결       |

체인 거래 증거, 상품 상태, 실제 잔액과 지급 의무 대사의 연결

```text
  거래 증거     상품 기록      계좌 증거        청구와 계약
```

### 6.4 예외 처리

- 지급이 예상과 다르게 진행되면 실패한 단계와 실제 자산 위치부터 확인함. 원래 거래를 보존한 채 상품별 복구, 반환과 분쟁 조건을 검토함

실패 대상과 자산 위치를 확인한 뒤 재시도, 반환과 분쟁 조건을 검토하는 순서

```text
[실패, 지연 또는 분쟁을 확인했음]
                 |
                 v
[어떤 대상에서 문제가 발생했는가]
                 |
       +---------+-----------+------------+
       |                     |            |
       v                     v            v
[지급 요청이나 승인]   [자산 이전]   [수취나 반환]
       |                     |            |
       +---------------------+------------+
                             |
                             v
              [현재 자산과 실행 결과를 확인함]
                             |
                             v
              [원래 의무와 기존 시도를 연결함]
                             |
              +--------------+--------------+
              |              |              |
              v              v              v
         [재시도 검토]  [반환 경로 확인] [분쟁 판단 확인]
              |              |              |
              +--------------+--------------+
                             |
                             v
              [실제 후속 결과를 기록하고 대사함]
```

**실패 판별**

- 견적, 심사, 제출과 실행, 현지 지급 및 반환 중 실패한 단계와 실제 자산 위치를 확인하며, 조회 장애를 실행 실패로 단정하거나 묶음 거래의 성공을 모든 하위 호출의 성공으로 해석하지 않음

| 실패 위치                  | 먼저 확인할 것                                                            | 가능한 처리와 조건                                              |
| -------------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 견적 또는 지급 생성 전     | 견적 만료, 가격과 송수신인 유형                                           | 새 견적을 요청하며 아직 생성되지 않은 지급과 체인 거래를 구별   |
| BFI 심사와 RFI             | 지급 상태, 추가 자료 및 승인 결과                                         | 자료를 보완하거나 종료 사유를 기록<br>지급 재생성의 조건을 확인할 필요가 있음 |
| 체인 제출과 확인           | 기존 거래 해시와 논스(nonce, 계정의 거래 순서 값), 실행 결과 및 지급 만료 | 포함 전 거래의 교체와 확정된 실패의 새 논스 재시도를 구별할 필요가 있음     |
| BFI 토큰 수령 후 현지 지급 | BFI의 토큰 수령과 현지 지급 결과                                          | 별도 토큰 반환과 고객 자금 복귀를 추적                          |
| 반환                       | 반환 객체와 해시, 입금 자산 및 금액                                       | 요청 접수와 실제 반환 완료를 구별                               |

**재시도**

- CPN의 Payment 실패에는 새 견적과 지급이 필요하지만, 유효한 Payment에 연결된 Transaction의 문제는 재생성, 교체나 가속의 대상이 될 수 있음. 먼저 체인 포함과 실행 여부, 실패 원인과 지급 만료를 확인하고 각 시도를 같은 청구에 연결하여 중복 지급을 방지해야 함
- 이미 확정된 실행 실패는 논스가 소비된 상태이므로 새 논스로 재시도해야 함. 아직 포함되지 않은 거래의 교체와 구별해야 하며, 실패한 실행의 실제 가스비도 비용에 포함해야 함

지급 실패와 체인 거래 문제를 구별하는 재시도 판단

```text
[다시 실행하기 전에: 무엇이 실패했는가]
    |
    +-- [Payment가 실패했음]
    |       새 견적과 새 지급을 만듦
    |       이전 지급과 새 지급을 같은 청구의 별도 시도로 남김
    |
    +-- [Payment는 유효하고, 체인 Transaction에 문제가 있음]
            포함 여부와 실패 원인에 따라 거래를 재생성, 교체하거나 가속함
            원래 거래와 교체 거래를 같은 지급의 시도로 연결함
            교체 거래가 실패해도 원래 거래는 실행될 수 있음
    |
    v
[어느 거래가 실제로 실행되었는지 확인하고, 같은 청구에 두 번 지급하지 않음]
```

**자금 반환**

- 반환 요청 접수, 실제 자산 전송, 수령 주체와 최종 고객의 자금 복귀를 따로 추적함. 원래 지급과 새 반환 거래를 함께 남기며, 반환 통화와 금액 및 후속 환전과 상환도 대조함

반환 도식: 상품별 송신 및 수령 주체와 최종 고객에게 자금이 복귀하기까지 남는 처리

```text
[자금 반환]
    |
    +-- 기관 지급 반환
    |       누가 어디로: BFI -> OFI, 새 반환 거래로 보냄
    |       고객에게 돌아오기까지 남는 것: OFI와 기업 사이의 환전, 수수료와 상환
    |
    +-- 수납 환불
    |       누가 어디로: 가맹점이 요청하고 Circle이 지정 주소로 보냄 (관리형 환불 기준)
    |       고객에게 돌아오기까지 남는 것: 그 주소가 실제 고객에게 닿는지
    |
    +-- 외환 미이행
    |       누가 어디로: FxEscrow -> 양쪽 기관, 담보와 거래 자금을 돌려주거나 보상함
    |       고객에게 돌아오기까지 남는 것: 담보가 손실을 모두 메우는지, 은행 자금으로의 상환
    |
    +-- 조건부 컨트랙트 반환
            누가 어디로: 컨트랙트나 판매자 잔액 -> 지급 전에 정한 반환 주소
            고객에게 돌아오기까지 남는 것: 주소 운영자의 고객 반영, 조기 인출 뒤의 부족 잔액

모든 반환에서 나누어 확인할 것
    요청을 받아들였는가 -> 자산을 보냈는가 -> 누가 받았는가 -> 최종 고객의 자금이 돌아왔는가
```

**기관 지급 반환**

- 현지 지급이 취소되거나 실패하면 수취 기관이 송신 기관에 토큰을 새 거래로 반환함. 원래 지급을 보존하고 기업에 돌려줄 통화, 금액, 수수료와 환율 및 상환 조건을 별도로 확인함

원래 전송, 새 반환 거래와 기업의 법정화폐 복귀의 구분

```text
원래 지급: [OFI USDC] ---- 확정 전송 ----> [BFI USDC]
                                                |
                                      [현지 지급 실패 또는 취소]
                                                |
별도 반환: [OFI USDC] <--- 새 반환 거래 --- [BFI USDC]
                |
       [기업에 돌려줄 통화와 금액 및 시점 확인]
```

**수납 환불**

- 일반 수납 상품의 환불 기한과 한도는 관리형 상품과 구별함. 미국과 싱가포르 법인의 반환 주소 및 원래 지급 연결 조건을 확인하고, 거래소 공동 주소로의 반환이 실제 고객에게 반영되는지도 확인함. 아래 VASP(virtual asset service provider)는 가상자산 서비스 사업자를 뜻함

상품과 법인별 환불 조건 및 고객에게 자금이 돌아왔는지 확인할 항목

```text
[수납 환불]
    |
    +-- [일반 Stablecoin Payments]
    |       기한: 결제 의향을 만든 뒤 30일 (입금 시각부터 세지 않음)
    |       조건: 계정의 반환 한도, refunded가 되면 새 수납을 받지 않음
    |
    +-- [Managed Payments, 미국 법인 경로]
    |       반환 주소: 체인 주소를 그대로 지정함
    |
    +-- [Managed Payments, 싱가포르 법인 경로]
            체인 주소를 그대로 지정할 수 없음
            방식 1: 원래 송신 주소로 돌려보냄 (원래 지급 ID를 함께 보냄)
            방식 2: 주소록에 등록한 새 주소로 보냄
                    (원래 지급 ID로 연결하고, 수령 측 VASP가 송신 측 VASP와 같아야 함)

모든 경로에서 확인할 것
    그 주소가 실제 고객에게 닿는가
        거래소의 공동 송신 주소에서 받은 납부라면, 그 주소로 돌려보내도
        원래 고객에게 반환되는지 알 수 없음
    요청을 접수한 시점과 토큰이 도착한 시점을 나누어 기록함
```

**외환 미이행**

- StableFX는 추가 자금 납부 여부에 따라 담보 반환이나 미이행 측 담보의 보상을 처리하지만 담보가 손실 전액을 보장하지 않으며, 문서 사이의 상태 대응과 토큰의 은행 상환은 별도로 확인할 필요가 있음

미이행 도식: 만기까지의 추가 자금 납부에 따라 인도, 담보 반환과 보상을 나눔

```text
[서명 뒤 거래 등록과 담보 예치]
    담보 비율과 최소 금액은 통화 쌍과 메이커 설정으로 정하며, 담보가 0일 수도 있음
          |
          v
[만기까지 각자 추가 자금을 넣었는가]
          |
          +-- 양쪽 모두 넣었음
          |       FxEscrow가 두 통화를 인도함
          |
          +-- 양쪽 모두 넣지 않았음
          |       컨트랙트가 양쪽의 담보를 돌려줌. 미이행 보상은 없음
          |
          +-- 한쪽만 넣었음
                  넣지 않은 쪽을 미이행 측으로 봄
                  넣지 않은 쪽의 담보 -> 넣은 쪽 (보상)
                  넣은 쪽의 담보와 거래 자금 -> 넣은 쪽 (반환)
```

**조건부 컨트랙트 반환**

- 지급 전에 고객의 보관 방식에 맞는 반환 주소를 정하고, 그 주소의 운영자가 고객에게 반환을 반영할 수 있는지 확인함. 반환 권한뿐 아니라 컨트랙트 잔액, 판매자의 조기 인출과 부족 자금의 부담 주체도 확인함

고객의 보관 방식에 따른 반환 주소와 조기 인출 뒤의 반환 가능성

```text
[지급 전에 정할 반환 주소]  고객이 자산을 어떻게 보관하는지에 따라 달라짐
    |
    +-- 거래소나 보관형 지갑을 거쳐 보냈음
    |       체인에는 고객이 아니라 그 사업자의 주소가 나타날 수 있음
    |       필요한 것: 그 사업자가 해당 고객의 반환으로 처리할 수 있는 주소
    |
    +-- 법정화폐로 내고 온램프 사업자를 거쳤음
            필요한 것: 그 온램프 사업자가 정한 반환 경로

    중재자가 반환 주소를 임의로 정하게 하면 비보관 구조가 아니게 됨
          |
          v
[반환을 실행할 수 있는가]
    반환 권한이 있음  +  반환할 자산이 남아 있음
                          판매자가 조기 인출했다면 잔액이 부족할 수 있음
                          -> 분쟁 처리
```

**분쟁 처리**

- 실패 증빙, 담당 기관, 계약상 의무와 컨트랙트의 기한, 손실 부담을 각각 확인함. Refund Protocol에서 조기 인출 뒤 중재자가 자기 자금으로 부족액을 충당하는 것은 선택 사항임. 교육용 소개나 개발 사례만으로 현재 배포된 코드의 감사 여부와 운영 준비가 입증되는 것은 아님

조기 인출 뒤 판매자 잔액이 부족한 경우의 중재자 환불과 채무 기록

```text
조기 인출
[중재자가 조기 인출을 허용하고 수수료를 정함]
          |
          v
[판매자가 인출 조건에 동의하는 서명을 체인 밖에서 만듦]
          |
          v
[컨트랙트가 그 서명을 체인에서 확인한 뒤 인출을 실행함]
          :
          :  나중에 환불이 필요해지면
          v
[판매자의 잔액으로 환불할 수 있는가]
          |
          +-- 잔액이 있음: 중재자가 판매자의 잔액에서 환불함
          |
          +-- 잔액이 부족함: 중재자가 자기 자금으로 환불할 수 있음
                               컨트랙트에 판매자의 채무를 기록하고 이후 지급으로 메움
```

### 6.5 대사

- 대사는 청구와 계약의 지급 의무에 실제 지급과 반환을 연결하고, 기록과 금액 및 중복을 확인하여 잔여 의무를 정리하는 업무임

기록 연결 뒤 금액과 중복을 확인하고 지급 의무를 대조하는 순서

```text
[입력] 6.3의 정상 처리 기록, 6.4의 재시도와 반환 및 분쟁 기록
    |
    v
[기록 연결]  청구에 견적, 지급, 거래, 은행 참조와 반환의 식별자를 잇음
    |
    +-- [금액 확인]  원금, 환율, 수수료와 반환 차액을 나눔
    |
    +-- [중복 판별]  같은 이동의 로그 두 개와 원래, 교체 거래를 한 번만 셈
    |
    v
[의무 확인]  실제 수취와 반환을 반영해 남은 지급 의무를 확인함
    |
    v
[출력] 업무 개선 효과의 확인에서 쓸 관측 자료
```

**기록 연결**

- 송장과 승인, 견적과 지급 시도, 체인 해시, 은행 참조 및 반환을 같은 청구에 연결하고 시각을 남김. 반복 수납 의향과 개별 납부를 구별하며, EOA의 직접 호출이 필요한 Memo의 식별자와 원래 호출 데이터를 앱의 대사 기록에 연결함

```text
[청구 또는 지급 의무]
          |
          +-> [견적 A -> 지급 시도 A -> 거래 A -> 결과]
          |
          +-> [견적 B -> 지급 시도 B]
                          |
                          +-> [원래 거래 B -> 결과 확인]
                          +-> [교체 거래 B -> 결과 확인]
                          +-> [현지 지급과 은행 참조]
                          +-> [반환 요청 -> 반환 거래 -> 반환 입금]
          |
          v
[실제 수취, 수수료와 환율 및 잔여 의무 대사]
```

**금액 확인**

- 청구, 송신, 실제 수취와 반환의 통화 및 금액을 비교하여 환율, 수수료와 미납을 구별함. USDC 이전 이벤트와 영수증의 가스비는 같은 단위로 환산한 뒤 별도로 집계함

```text
[원래 청구 금액]        송장과 계약이 정한 통화와 금액
        |
        |  확인할 것: 견적이 송신 고정인가 수취 고정인가, 환율, 포함 수수료
        v
[송신 기관이 사용한 금액]
        |
        |  확인할 것: 기관의 지급, 현지 지급과 은행 처리의 기록
        v
[실제 수취 금액]        수취인의 계좌나 지갑에 도착한 금액
        :
        :  반환이 있으면
        v
[반환 금액]             별도 반환 거래로 들어온 금액. 원래 지급의 기록은 지우지 않음

차이를 나눌 원인: 수수료 / 환율 / 미납 / 반환
가스와 은행 비용은 다른 장부에 생길 수 있음
같은 통화끼리만 빼고 더함. 다른 통화는 사용한 시점과 환율을 기록한 뒤 환산함
```

**중복 판별**

- Arc USDC의 ERC-20 소수 6자리 로그와 네이티브 소수 18자리 로그를 같은 이동으로 연결함. Memo와 묶음 호출의 부가 이벤트를 별도 지급으로 세지 않으며, 원래 거래와 교체 거래는 실제 자산 이전 결과를 기준으로 대조함

```text
[ERC-20 transfer() 호출 한 번]
          |
          +-- [ERC-20 USDC 컨트랙트의 Transfer 로그]   소수 6자리
          |
          +-- [시스템 방출 주소의 Transfer 로그]   소수 18자리
          |
          v
[같은 이동 한 건으로 셈]
    방출 주소로 두 로그를 구별하고, 6자리 값과 18자리 값을 섞지 않음

[네이티브 전송 한 번] -> [시스템 방출 주소의 Transfer 로그] 하나만 생김

[재시도의 원래 거래와 교체 거래] -> 실제 자산 이전에 성공한 결과를 확인하여 집계함
```

- 자산 이전액은 실제 성공한 이전 결과로 집계하고, 가스비는 확정된 실행 실패를 포함한 각 시도의 실제 비용으로 집계함. 같은 논스의 교체와 새 논스의 재시도를 구별하며, 여러 거래가 실제로 자산을 이전했다면 중복 지급 여부를 확인해야 함

## 8. 종합 판단

- 기업 지급의 완료 여부는 체인 거래의 확정만으로 판단할 수 없으며, 약속한 자산의 실제 수취와 지급 의무 및 기록의 대사가 필요함
- Arc의 직접 역할은 공유 상태에서 자산 이전과 컨트랙트 실행 결과를 확정하는 것임. USDC 가스와 빠른 확정은 해당 구간의 자산 관리와 대기 부담을 줄일 수 있지만, 기관 심사, 현지 지급, 고객자금의 법적 보호와 외환 규제는 별도로 확인해야 함
- Circle 제품은 자금 준비, 견적, 서명, 이전과 현지 지급을 연결하는 수단임. Arc에서 이용할 수 있는지와 실제 업무에 적용할 수 있는지는 제품, 체인, 통화와 기관의 지원 조건에 따라 달라짐
- 경제적 지속 가능성은 앱 사업자와 직접 거래하는 주체의 효용 및 비용, 검증자의 수입과 운영 부담, Circle과 앱 사업자의 사업 수익을 구분하여 판단해야 함. ARC 토큰 백서의 기능 제안도 실제 구현, 수수료 귀속, 보상과 공급 변화 및 참여자의 부담을 함께 확인해야 함
- 따라서 적용 여부를 판단하려면 동일한 지급 업무의 기존 경로와 비교하여 전체 비용, 실제 수취까지 걸린 시간, 자금 준비 부담과 예외 처리 결과를 관측할 필요가 있음. 이 글에서 정리한 구조와 조건만으로 실제 개선 효과, 참여자의 수익성이나 ARC 토큰의 적정 가격을 확정할 수는 없음
