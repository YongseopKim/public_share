# Arc의 현재 상태: 네트워크, 제품과 실제 사용을 확인하고 참가 조건을 판단한다

Arc의 기본 네트워크에는 공개 메인넷 출시 발표와 읽기 전용 RPC(Remote Procedure Call, 원격 프로시저 호출) 응답이 있다. 그러나 기본 네트워크의 제공, 금융 상품의 계정 승인, 기관 고객의 업무와 미래 기능의 개발은 서로 다른 질문이다. 이 문서는 그 차이를 설명하고, 필요한 기능을 참가 기간에 사용할 수 있는지 판단할 때 어떤 조건을 확인해야 하는지 연결한다.

현재 상태의 기준은 2026-10-05에 확보한 출시 자료와 RPC, 그리고 2026-10-06 KST에 다시 읽은 운영자 상태 및 일정과 외부 집계다. 다른 날짜의 자료를 하나의 동시 측정으로 합치지 않는다.

프로그램 목적과 제품 요구에는 2026-10-07에 수집한 과거와 현행 공고를 보충했다. 수집 자료의 재구성은 공고의 표현을 재구성한 자료이며 전체 행사 전수 목록과 현재 접수 가능성을 확정하지 않는다. 이 보충으로 기존 네트워크와 제품 상태를 새 시점의 관측으로 바꾸지는 않는다.



아래 개요와 각 절의 추가 표는 본문의 관계를 내가 정리한 것이다. Circle의 공식 분류나 새로운 실행 검증 결과는 아니다.

한국어:

```text
                     [판단 기준]
                   대상 / 근거 / 시점
                          |
         +----------------+----------------+
         |                |                |
    [네트워크 상태]  [제품 상태]      [접근 조건]
     어떤 환경인가    어떤 기능인가    누가 이용하는가
         |                |                |
         +----------------+----------------+
                          |
            [필요한 기능의 이용 가능성]
                          |
                          v
                    [참가 조건과 대조]
                일정 / 제출 / 선정 / 지급
                          |
                          v
                   [참가에 관한 판단]

 [사용 현황: 같은 판단 기준 적용]
  자금 / 거래 / 기관 참여
            |
            v
  [실제 업무와 성과에 관한 판단]

      [참가에 관한 판단] + [실제 업무와 성과에 관한 판단]
                          |
                          v
                   [판단 범위의 정리]
                확인한 범위 / 남은 질문
```

English:

```text
                       [Assessment criteria]
                     Object / Evidence / Time
                                |
            +-------------------+-------------------+
            |                   |                   |
     [Network status]    [Product status]     [Access conditions]
     Which environment?  Which function?     Which user?
            |                   |                   |
            +-------------------+-------------------+
                                |
                 [Usability of the needed function]
                                |
                                v
                 [Compare participation conditions]
              Dates / Submission / Selection / Payment
                                |
                                v
                   [Participation assessment]

    [Usage evidence: apply the same criteria]
    Funds / Trades / Institutional participation
                     |
                     v
          [Business use and outcome assessment]

 [Participation assessment] + [Business use and outcome assessment]
                                |
                                v
                      [Scope of conclusions]
                   Supported scope / Open questions
```

연결선은 판단에 쓰는 관계를 나타내며, `+`는 두 판단을 함께 검토한다는 뜻이다. 네트워크와 제품의 제공 및 이용자의 접근 조건은 참가 판단에 연결하고, 사용 현황은 실제 업무와 성과 판단에 연결한다. 두 판단의 근거와 시점을 구별하여 마지막 판단 범위를 정리한다.

검증자(validator)의 지정 명단과 실제 합의 참여를 구별한다. 최종성(finality)의 설계 설명도 특정 운영 기간에 실제로 측정한 결과와 같지 않다. 총예치가치(TVL, Total Value Locked), 시가총액(market capitalization), 거래량(volume)은 서로 다른 관측값이다. 단계적 도입(phased rollout)과 운영 또는 탐색(live on or exploring)의 표현은 확정 운영을 뜻하는 하나의 상태로 합치지 않는다.

## 1. 판단 기준: Arc의 현재 상태를 어떤 대상과 근거로 설명할 것인가

현재 상태를 설명하려면 확인할 대상과 근거, 시점을 먼저 구별해야 한다. 아래 기준은 네트워크와 제품을 읽을 때뿐 아니라 실제 사용과 프로그램 참가를 판단할 때도 적용한다.

| 판단하려는 질문              | 확인할 대상            | 필요한 근거             | 별도로 남는 질문                           |
| ---------------------------- | ---------------------- | ----------------------- | ------------------------------------------ |
| 네트워크가 공개되었는가?     | 출시 단계와 적용 환경  | 출시 발표와 환경별 문서 | 내 환경에서도 실행되는가?                  |
| 특정 기능이 제공되는가?      | 제품, 자산과 버전      | 지원 문서와 배포 상태   | 내 계정이 이용할 수 있는가?                |
| 내가 이용할 수 있는가?       | 권한, 자격과 실행 준비 | 계정 조건과 실행 기록   | 선택한 경로를 지속적으로 이용할 수 있는가? |
| 실제 업무에 쓰이는가?        | 고객, 목적과 이용 기간 | 업무별 이용 기록        | 비용이나 오류를 줄였는가?                  |
| 프로그램에 참가할 수 있는가? | 일정, 자격과 제출 요건 | 주최 조건과 내 결과물   | 선정과 지급까지 가능한가?                  |

각 행은 하나의 판단 질문이다. 모든 근거는 적용 환경과 기준 시점을 함께 읽는다.

### 1.1 확인 대상: 네트워크, 제품과 이용자에 관한 질문은 답의 대상과 필요한 자료가 다르다

"Arc가 메인넷인가?"라는 질문은 기본 네트워크의 공개 여부를 묻는다. "내 계정으로 StableFX(토큰 외환 교환 서비스)를 쓸 수 있는가?"라는 질문은 특정 상품의 승인과 통화쌍을 묻는다. "기관 고객이 정기적으로 지급하는가?"라는 질문은 고객 업무의 관측을 묻는다. 같은 Arc에 관한 질문이어도 답의 대상과 필요한 자료가 다르다. StableFX의 상세 정의는 기업 업무 설명에 있다.

한 기능이 공개 문서와 테스트 환경을 제공해도 특정 계정의 메인넷 실행은 미확인일 수 있다. 반대로 기관 상품에 승인 조건이 있다고 기본 체인의 모든 계약 배포까지 기관 승인제라고 할 수는 없다. 각 행위를 고정하면 제공과 미확인이 어디에 함께 존재하는지 알 수 있다.

### 1.2 확인 근거: 발표, 접근 권한, 실행과 고객 사용은 각각 다른 질문에 답하며 서로를 대신하지 않는다

확인 대상을 정한 다음에는 어떤 근거가 그 질문에 답하는지 구별해야 한다. 이를 설명하려고 나는 세 답변이 반복한 네 가지 관계를 함께 기록한다. 발표와 문서는 제공자의 설명을, 접근과 자격은 해당 참가자의 허용 범위를, 실행과 관측은 확인한 응답을, 고객 사용은 실제 업무의 이용을 다룬다. 이 구분은 내가 설명을 위해 구성한 것이며 Circle의 공식 성숙도 단계가 아니다.

다음 그림은 ChatGPT의 기능표와 Claude의 제공 구분, Grok의 관측 경계를 내가 연결한 것이다. 선은 특정 기능에 관한 자료를 모은다는 뜻이다. 발표를 읽으면 자동으로 실행과 고객 사용까지 확인된다는 순서가 아니다.

한국어:

```text
                     [특정 기능/환경/버전]
                               |
          +-----------+--------+---------+-----------+
          |           |                  |           |
          v           v                  v           v
     [발표/문서]  [접근/자격]       [실행/관측]  [고객 업무 사용]
          |           |                  |           |
          +-----------+--------+---------+-----------+
                               |
                               v
               [시점과 확인 범위를 가진 상태 설명]
```

English:

```text
                   [Specific function/environment/version]
                                      |
              +-----------+-----------+----------+-------------+
              |           |                      |             |
              v           v                      v             v
        [Announcement] [Access/eligibility] [Execution/data] [Customer use]
        [Documentation]
              |           |                      |             |
              +-----------+-----------+----------+-------------+
                                      |
                                      v
                   [Dated status with inspected scope]
```

어느 상자의 근거가 비어 있다면 그 질문이 미확인이다. 예를 들어 읽기 응답은 확인했지만 고객의 사업 종류를 모르면 고객 사용이 미확인이다. 이를 기본 체인의 부재나 고객 성공의 확인으로 바꾸지 않는다.

### 1.3 확인 시점: 게시일, 사건일과 관측일은 서로 다른 기록이며 하나로 합치지 않는다

게시일은 글이 나온 날이다. 사건일은 그 글이 말하는 출시, 변경이나 제출이 발생하는 날이다. 관측일은 조사자가 응답이나 페이지를 읽은 날이다. 출시 전 예고를 읽은 날과 실제 출시 발표일, 이후 RPC를 조회한 날은 각각 다른 기록이다.

이 구별은 과거 자료를 잘못된 자료로 버리지 않게 한다. 예고 당시의 "앞으로 출시한다"는 문구는 당시 계획을 설명한다. 뒤의 출시 발표와 함께 읽으면 어떤 계획이 어떤 사건 발표로 이어졌는지 볼 수 있다. 반대로 일정 하나가 지켜졌다는 사실에서 다른 미래 일정의 이행까지 보장할 수는 없다.

프로그램에서도 같은 구별이 필요하다. 목록의 행사 종료, 제출 마감과 심사 결정 및 실제 지급은 다른 사건이다. 날짜가 같거나 시간대 환산으로 같은 날이 되어도 필드의 의미를 합치지 않는다. 뒤의 참가 기간 설명에서 이 원칙을 구체적으로 적용한다.

## 2. 네트워크 상태: 공개 출시와 실제 운영을 어디까지 확인했는가

앞의 기준을 기본 네트워크에 적용한다. 출시 단계와 실행 환경을 구별한 뒤 운영 관측의 한계를 설명하고, 접속 주소 변경이 이용자에게 요구하는 조치를 확인한다.

| 자료 종류           | 직접 확인하는 내용               | 별도 확인이 필요한 내용        |
| ------------------- | -------------------------------- | ------------------------------ |
| 출시 예고           | 제공자가 설명한 계획과 예정 조건 | 실제 출시 여부                 |
| 출시 발표           | 제공자가 발표한 출시 사건과 범위 | 이용자별 실행 성공             |
| RPC 응답            | 특정 주소, 요청과 시점의 응답    | 모든 기능의 성공과 지속 운영   |
| 운영 상태 보고      | 운영자가 보고한 구성요소의 상태  | 모든 지역과 계정의 이용 결과   |
| 접속 주소 변경 공지 | 변경 대상과 예정 조치            | 실제 시행과 이용자의 설정 변경 |

각 행은 자료의 종류이며, 발표와 관측의 확인 범위를 비교한다.

### 2.1 출시 단계: 공개 메인넷 출시는 2026-09-16에 발표됐고, 그 전의 비공개 운영과 구별한다

[Arc의 2026-08-05 글](https://www.arc.io/blog/arc-mainnet-goes-live-on-september-16-2026)은 9월 16일 메인넷 출시를 예고했고, 공개 전에 비공개 메인넷을 탐색하거나 이용하는 빌더를 설명했다. [Circle의 2026-09-16 발표](https://www.circle.com/pressroom/circle-launches-arc-mainnet-an-economic-operating-system-for-the-internet)는 공개 메인넷 출시를 발표한다. 두 문서를 함께 읽으면 예고와 발표를 연결할 수 있다.

공식 글 연결: [Arc Mainnet Launches September 16, 2026](https://www.arc.io/blog/arc-mainnet-goes-live-on-september-16-2026) (2026-08-05, [공식 원문](https://www.arc.io/blog/arc-mainnet-goes-live-on-september-16-2026)). 메인넷 예고 글을 통해 발표 시점과 예정일을 다시 확인할 수 있다. 예고 자체를 출시 사건의 독립 확인으로 읽지 않는다.

공개 전 운영은 공개 출시와 다르다. 따라서 블록 높이에 공개 전 구간이 포함되는지 모르는 상태에서 높이를 공개 출시 이후의 일수로 읽으면 안 된다. 또한 9월 발표에 등장한 앱과 기관이 모두 같은 방식으로 유료 고객 업무를 운영했다고 결론낼 수 없다. 발표의 동사는 뒤에서 따로 읽는다.

다음 시간선은 ChatGPT의 긴 이정표 그림에서 표현 방식을 참고해 내가 다시 구성했다. 이 그림에는 이번에 다시 읽은 예고, 공개 발표와 보존 응답만 놓았다. ChatGPT 그림의 다른 이정표는 7.3(보류 내용)에 남겼다.

한국어:

```text
 [2026-08-05 예고]        [2026-09-16 공개 출시 발표]
 공개 전 운영 설명   --->  공개 메인넷 사건의 회사 발표
                                   |
                                   v
                         [2026-10-05 읽기 응답]
                         환경별 체인 ID와 블록 값
                                   |
                                   v
                         [2026-10-06 KST 재확인]
                         운영자 상태, 일정과 외부 집계
```

English:

```text
 [2026-08-05 schedule]       [2026-09-16 public launch announcement]
 Pre-public operation --->  Company announcement of public mainnet
                                         |
                                         v
                               [2026-10-05 read responses]
                               Chain IDs and block values
                                         |
                                         v
                               [2026-10-06 KST inspection]
                               Operator status, dates, external metrics
```

화살표는 자료를 시간 순서로 읽는 연결이다. 각각의 관측이 앞의 사건 전체를 독립적으로 검증한다는 뜻은 아니다.

### 2.2 실행 환경: 메인넷과 테스트넷은 서로 다른 chain ID로 응답하며, 문서의 범위와 선택한 환경을 함께 확인한다

RPC(Remote Procedure Call, 원격 프로시저 호출)는 네트워크에 값을 요청하는 방법이다. 당시 조회한 공개 RPC 응답에는 요청 URL과 method, 요청 및 수신 시각과 HTTP 응답 및 JSON 결과가 있다. 거래 서명이나 전송 없이 체인의 식별자와 블록 값을 읽었다. 서명한 거래는 2026-10-07 테스트넷 실험에서 실행했다. 실험은 chain ID 5042002의 테스트넷에서 계약 배포 두 건, 계약 호출 한 건과 USDC 전송 두 건에 서명해 보냈고, 다섯 건 모두 블록에 포함됐다. 전송 코드는 위 표의 테스트넷 주소(`https://rpc.testnet.arc.io`)에 연결했다. 배포와 호출은 Foundry의 네트워크 설정을 썼으므로 실험 출력에 주소가 남지 않았다. 메인넷에서 서명한 거래는 이 연구에서 실행하지 않았다.

| 환경    | 요청한 기본 주소             | 응답의 체인 ID와 정수 변환 | `eth_blockNumber` 결과와 정수 변환 |
| ------- | ---------------------------- | -------------------------- | ---------------------------------- |
| Mainnet | `https://rpc.mainnet.arc.io` | `0x13b2` = 5042            | `0x173c9c6` = 24,365,510           |
| Testnet | `https://rpc.testnet.arc.io` | `0x4cef52` = 5042002       | `0x3e8fad7` = 65,600,215           |

요청은 2026-10-05 08:58:26 UTC부터 순차적으로 수행됐다. `eth_blockNumber`와 다음 `eth_getBlockByNumber`의 높이가 다를 수 있으므로 여러 필드를 같은 순간의 단일 블록이라고 합치지 않는다.

[연결 문서](https://docs.arc.io/arc/references/rpc-endpoints.md)는 메인넷 5042와 테스트넷 5042002를 각각 명시한다. 반면 [개요 페이지](https://docs.arc.io/arc-chain.md)는 앞에서 두 환경을 소개한 뒤 세부 표에 테스트넷 시간과 5042002를 둔다. 배포자는 전체 소개 문구만 읽고 그 ID를 메인넷에 복사하면 안 된다. 문서의 범위와 실제 선택 환경을 함께 확인해야 한다.

이 차이는 페이지를 단일 상태표로 읽기 어렵게 하지만 수정 지연의 원인까지 알려주지는 않는다. 수정 이력을 확인하지 않은 상태에서 "업데이트가 늦었다"는 해석을 역사 사실로 쓰지 않는다. 원고는 실제 응답과 환경별 연결 문서를 기준으로 구별한다.

### 2.3 운영 관측: 블록 높이와 상태 보고만으로는 운영 기간이나 무중단 운영을 증명하지 못한다

Grok 답변은 높이를 "0.5초로 나누면" 기간을 얻는다고 적었다. 높이의 단위가 block이고 간격이 seconds/block이면 두 값을 곱해야 seconds가 된다.

```text
가정: 높이가 처음부터 센 블록 수이고, 모든 간격이 0.5초다.
기간(일) = 블록 수 * 0.5초/블록 / 86,400초/일

Grok 답변의 메인넷 높이: 24,355,983 * 0.5 / 86,400 = 약 140.95일
Grok 답변의 테스트넷 높이: 65,590,762 * 0.5 / 86,400 = 약 379.58일

공개 출시 발표에서 Grok 답변의 관측일까지:
2026-10-05 - 2026-09-16 = 19일
```

두 기간의 차이가 비공개 운영의 정확한 길이를 측정한 것은 아니다. 출발 높이, 전체 간격과 중단, 공개 전 운영 기록이 미확인이다. 단위를 고친 계산도 그 입력 가정이 확인되지 않으면 제네시스 날짜를 증명하지 못한다. 다른 섹션의 조회 높이와 차이를 내더라도 정확한 조회 시각이 없으면 생성 속도나 무중단 운영을 측정할 수 없다.

[새 상태판 응답](https://status.arc.io/api/v2/summary.json)은 Mainnet, Testnet와 Arc Portal의 구성요소를 operational로 보고한다. 이는 운영자가 선택한 항목의 상태 보고다. 공개된 과거 기간에 장애 보고가 보이지 않는다는 사실도 모든 장애의 부재나 모든 지역 및 계정의 성공을 증명하지 않는다. Grok 답변이 받은 RPC 403과 다른 응답의 성공은 URL과 시각 및 요청 조건을 보존한 채 비교해야 한다.

### 2.4 운영 변경: 주소 변경 공지는 옛 testnet 주소 네 개를 쓰는 이용자에게만 적용된다

관측한 운영 상태와 이후의 접속 조건도 구별해야 한다. 네트워크 전체의 상태와 별개로, 특정 주소를 이용하는 개발자에게는 주소 변경이 필요할 수 있다.

[운영자 공지](https://status.arc.io/api/v2/scheduled-maintenances/upcoming.json)는 옛 testnet 주소에 대해 2026-10-08 00:00부터 10-09 00:00 UTC까지 요청이 실패할 수 있다고 예고하고, 10월 15일 제거를 예고한다. 브라운아웃(brownout)은 이전 주소의 이용자에게 변경을 알리기 위해 요청 중단 가능성을 두는 조치다. 관측 기준일에는 예정 공지이며 실제 시행 확인은 후속 관측이다.

| 공지가 지정한 옛 testnet 주소         | 대응하는 새 주소                 |
| ------------------------------------- | -------------------------------- |
| `rpc.testnet.arc.network`             | `rpc.testnet.arc.io`             |
| `rpc.quicknode.testnet.arc.network`   | `rpc.quicknode.testnet.arc.io`   |
| `rpc.drpc.testnet.arc.network`        | `rpc.drpc.testnet.arc.io`        |
| `rpc.blockdaemon.testnet.arc.network` | `rpc.blockdaemon.testnet.arc.io` |

이 표는 공지의 정확한 대상이다. mainnet와 새 arc.io 주소도 같은 시간에 종료된다고 넓히지 않는다. 프로젝트가 옛 주소를 쓰는지 확인한 뒤 해당 설정과 예제의 주소를 바꾸면 된다. 운영 주소 변경을 ARC 공개 출시나 프로그램 제출 일정으로 읽지도 않는다.

## 3. 제품 상태: 어떤 기능이 제공되며 어떤 기능이 개발 중인가

네트워크가 응답한다는 관측만으로 그 위의 모든 제품을 사용할 수 있다고 판단할 수는 없다. 사용할 제품의 자산과 처리 경로를 고정하고, 현재 제공 기능과 개발 중인 기능을 구별한다.

| 기능 또는 제품                                                           | 지원 범위를 읽는 단위                 | 본문이 구별하는 제공 상태                      | 실제 이용 전에 확인할 내용                                    |
| ------------------------------------------------------------------------ | ------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------- |
| 기본 체인 개발                                                           | 네트워크, 지갑과 대상 계약            | 공개 네트워크의 읽기와 계약 실행을 구별한다.   | 가스 자금과 대상 계약의 성공 및 실패                          |
| CCTP(Cross-Chain Transfer Protocol, Circle의 체인 간 토큰 이동 프로토콜) | 자산, 출발 및 목적 체인과 계약 버전   | 이동 설명과 선택 경로의 실행을 구별한다.       | 출발 처리, 증명(attestation)과 목적 체인의 발행(mint) 및 복구 |
| Gateway 및 Unified Balance                                               | 자산과 체인별 예치 및 실행 경로       | 제공 설명과 자산별 예정 조합을 구별한다.       | 현재 지원 조합과 실제 계정 잔액                               |
| App Kits                                                                 | kit, 버전과 송금, 교환 또는 수납 경로 | SDK의 제공과 개별 경로의 이용을 구별한다.      | 인증, 키, 환경과 웹앱 정책                                    |
| Portal                                                                   | 자산과 대출, 수익 또는 온램프 경로    | 접근 창구의 소개와 상품별 이용을 구별한다.     | 지역, 제삼자 프로토콜과 자격 요건                             |
| AgentVM과 네트워크 프라이버시                                            | 미래 실행 환경과 적용 기능            | 설계 또는 개발 중 설명과 공개 제공을 구별한다. | 실제 릴리스, 배포 환경과 접근 및 호출                         |

각 행은 기능 또는 제품의 확인 단위다. 아래 본문의 지원 범위와 개발 단계 설명을 함께 대조하며, 전 경로의 실행 성공을 뜻하지 않는다.

### 3.1 지원 범위: 제품이 제공되어도 필요한 자산, 체인과 처리 경로의 조합은 따로 확인한다

"체인 간 이동을 제공한다"는 설명에는 어느 제품으로 어떤 자산을 어디에서 어디로 옮기는지가 빠져 있다. USDC(Circle이 발행하는 미국 달러 스테이블코인)의 소각 및 발행(burn-and-mint) 경로와 다른 자산의 잠금 및 표현 방식도 같지 않다. 제품 출시 발표가 있어도 자산별 지원표에는 예정 조합이 남을 수 있다.

CCTP(Cross-Chain Transfer Protocol)는 Circle의 체인 간 토큰 이동 프로토콜이다. Gateway 및 Unified Balance는 여러 체인의 USDC를 예치하고 통합 잔액으로 사용할 수 있도록 연결한다. App Kits는 이런 동작을 앱에 넣는 SDK(Software Development Kit, 소프트웨어 개발 도구 묶음)다. 아래 표는 기능별로 확보한 설명과 남은 이용 조건을 구별한다.

공식 글 연결: [Arc Mainnet Is Here: The Economic OS for the Internet Is Now Live](https://www.arc.io/blog/arc-economic-os-internet) (2026-09-16, [공식 원문](https://www.arc.io/blog/arc-economic-os-internet)). 출시 글은 초기 App Kits 이후 추가된 제품들을 소개한다. 제공자가 소개한 지원 범위와 특정 계정 및 경로의 실행 성공은 구별한다.

| 확인할 기능                    | 확보한 설명과 연결                                                                 | 실제 이용 전에 남는 조건                                              |
| ------------------------------ | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 기본 체인 읽기 및 계약 개발    | 환경별 RPC 문서와 보존 응답이 있다.                                                | 지갑 설정, 가스 USDC와 대상 계약의 성공 및 실패를 직접 확인한다.      |
| CCTP의 USDC 이동               | 사용 승인(approve), 소각(burn), 증명(attestation)과 발행(mint)은 서로 다른 단계다. | 출발과 목적 체인, 계약 버전과 처리 시각 및 목적 단계 복구를 고정한다. |
| Gateway 및 Unified Balance     | 예치된 잔액과 각 체인에서 실행한 자산 이전을 구별한다.                             | 자산, 환경과 현재 지원 조합 및 실제 계정 잔액을 확인한다.             |
| App Kits의 송금, 교환과 수납   | 문서상 제공되는 SDK와 인증 및 환경의 조건이 있다.                                  | 특정 kit와 버전 및 경로의 지원, 키와 웹앱 정책을 별도로 확인한다.     |
| Portal의 대출과 수익 및 온램프 | 제공자 발표는 사용자의 접근 창구로 소개한다.                                       | 지역, 대상 자산과 제삼자 프로토콜 및 자격 요건을 각각 확인한다.       |

이 표는 확인한 관계를 모은 것이며 모든 조합을 시험한 결과표가 아니다. Grok 답변은 EURC(Circle의 유로 스테이블코인)와 cirBTC(Circle의 비트코인 기반 토큰)의 일부 Gateway 및 Nanopayments 경로에 예정 표시가 있다고 보고했다. 그 표의 특정 조합을 다른 자산의 실행 성공으로 바꾸지 않는다. 현재 행위를 결정할 때는 최신 지원표와 실제 호출을 다시 대조해야 한다.

지원 범위를 읽는 데에는 제품의 역할도 중요하다. CCTP는 자산을 체인 사이에서 옮기는 처리 경로이고, Gateway는 예치된 자금의 통합 이용을 연결하며, App Kits는 앱이 그러한 기능을 호출하도록 돕는다. Portal은 사용자가 상품에 접근하는 화면이다. 따라서 SDK나 화면이 제공된다는 설명과 그 안에서 선택한 자산의 이동, 교환 또는 대출이 가능한지는 함께 확인해야 한다. 같은 Circle 패키지 안에서도 Send, Bridge, Swap과 Onramp의 지갑 및 인증 조건은 기능별로 확인해야 한다.

예를 들어 USDC를 다른 체인에서 Arc로 옮겨 특정 앱에서 쓰는 참가안을 가정해 보자. 여기에는 출발 체인의 자산, Arc를 목적지로 하는 이동 경로, 목적 지갑과 앱의 계약이라는 서로 다른 대상이 있다. 이동 제품이 제공되더라도 출발 자산과 체인 조합이 맞지 않으면 그 경로를 사용할 수 없다. 자금이 도착했더라도 앱의 계약이 다른 환경에 배포되었거나 상품 자격을 요구하면 다음 행동이 막힐 수 있다. 이 예시는 상태표를 참가안에 적용하는 나의 설명이며 실제 사용자의 실행 결과는 아니다.

이렇게 필요한 행위를 구체화하면 미확인의 위치도 좁힐 수 있다. 제품 전체가 미확인인지, 필요한 자산 조합만 예정인지, 계정 승인이나 실제 호출만 남았는지에 따라 후속 자료가 달라진다. 지원 조합은 제품 상태에서, 해당 이용자의 승인과 실행 준비는 다음 접근 조건에서 설명한다.

### 3.2 개발 단계: 개발 중이거나 로드맵에 있는 기능은 현재 제공 기능과 따로 판단한다

출시 발표는 Circle Agent Stack과 Agent Wallets, Portal의 지출 한도 및 위임을 소개한다. AgentVM은 설계 중인 환경으로 설명한다. 현재의 지갑 정책을 이용하는 앱과 민감한 데이터 및 신원을 다룰 미래 실행 환경은 다른 의존성이다.

프라이버시도 [출시 발표](https://www.circle.com/pressroom/circle-launches-arc-mainnet-an-economic-operating-system-for-the-internet)의 `in development for network-wide release` 조건을 유지한다. 프로토콜 설명이 설명한 설계와 신뢰 조건을 현재 모든 계약이 기밀 실행된다는 사실로 바꾸지 않는다. 페이지에서 개발 중 문구가 사라졌다면 실제 공개 환경과 코드 및 접근을 다시 확인해야 한다.

같은 원칙이 에이전트 전용 환경인 Agent Sector와 지분증명(Proof of Stake, PoS) 및 ARC에 적용된다. 여러 검증자가 동시에 블록을 제안하는 다중 제안자(multi-proposer)도 마찬가지다. Grok 답변은 이를 AMP(Arc Multi-Proposer Protocol)라는 이름으로 소개했지만, 합의 문서는 로드맵 항목으로 적을 뿐 제공 시점을 밝히지 않는다. 2027년 전환 탐색과 민트 발표의 공개 출시 비확약은 확정 전환일이나 개인 배분권이 아니다. 에이전트 신원 표준의 주소 및 예제 하나가 있거나 보이지 않는다는 사실만으로 다른 모든 구현의 존재와 부재도 판정하지 않는다.

공식 글 연결: [Arc Mainnet Is Here: The Economic OS for the Internet Is Now Live](https://www.arc.io/blog/arc-economic-os-internet) (2026-09-16, [공식 원문](https://www.arc.io/blog/arc-economic-os-internet)). 출시 글은 초기 민트가 ARC의 공개 출시 약속이 아니며 PoS 전환을 탐색한다고 설명한다. 확정 전환일이나 개인의 토큰 배분권을 뜻하지 않는다.

현재 지갑에 지출 한도와 위임을 설정하는 기능은 누가 어떤 자금 이동을 승인할지를 다룬다. AgentVM과 네트워크 프라이버시의 개발 설명은 앞으로 어떤 실행 환경에서 데이터를 처리할지를 다룬다. 목적이 연결되어도 같은 구현은 아니다. 현재 지갑 정책으로 승인 범위를 제한하는 앱을 만드는 일과, 개발 중인 환경이 이미 민감한 데이터를 보호한다고 전제하는 일은 서로 다른 근거를 요구한다.

참가 기간에 이 차이를 적용할 때는 필요한 기능을 핵심 동작과 후속 확장으로 나누어 설명할 수 있다. 현재 제공 기능으로 무엇을 시연하며, 개발 중 기능이 제공된다면 무엇을 추가할 수 있는지를 명시하는 방식이다. 이는 내가 일정 의존성을 설명하기 위한 구분이다. 미래 기능을 기다려야만 성립하는 부분은 현재 실행 결과에 포함하지 않고, 별도의 설계와 의존성으로 남긴다. 기능의 실제 제공을 다시 판단하려면 발표뿐 아니라 적용 환경과 접근 조건 및 호출 결과를 함께 확인해야 한다.

## 4. 접근 조건: 누가 어떤 자격과 준비를 갖추어 이용할 수 있는가

제품의 지원 범위를 확인한 다음에는 해당 이용자가 실제로 접근할 수 있는지 확인한다. 이용 권한과 자격을 구별하고, 권한을 확보한 뒤 실행에 필요한 지갑과 자금 및 환경을 살펴본다.

| 접근 조건 | 확인할 질문                                  | 확인할 자료 또는 결과                 |
| --------- | -------------------------------------------- | ------------------------------------- |
| 이용 권한 | 해당 기능을 호출하거나 사용할 권한이 있는가? | API 권한, 계정 승인과 서비스 조건     |
| 이용 자격 | 지역과 개인 또는 기관 조건을 충족하는가?     | 상품별 자격과 계정 상태               |
| 지원 조합 | 필요한 자산과 경로를 지원하는가?             | 자산, 네트워크와 버전별 지원표        |
| 실행 준비 | 지갑, 자금과 접속 환경이 준비되었는가?       | 지갑 설정, 접속 주소와 자금 취득 경로 |
| 실제 실행 | 선택한 조건에서 요청이 성공하는가?           | 응답, 거래 결과와 실패 처리 기록      |

각 행은 이용자의 경로를 확인할 조건이다. 일부 조건은 함께 확인할 수 있으며, 고정된 승인 순서나 사용자의 확인 완료를 나타내지 않는다.

### 4.1 이용 권한: 공개 RPC로 기본 체인을 개발할 수 있어도 금융 상품은 계정 승인이 따로 필요하다

StableFX는 외환 호가와 교환을 제공하는 상품이고, CPN(Circle Payments Network)은 참여 금융기관의 지급 업무를 연결한다. Mint는 적격 고객의 법정화폐와 토큰 발행 및 상환을 다룬다. 이들은 공개 체인에 기본 계약을 배포하는 행위와 같은 계정 자격을 요구한다고 볼 수 없다.

기업 업무 설명이 설명한 StableFX의 선택 통화쌍과 승인, CPN의 금융기관 접근과 Mint의 계좌 조건을 함께 유지한다. 메인넷 발표의 `active or onboarding` 자산 목록도 모든 자산의 모든 쌍을 지금 내 계정에서 교환할 수 있다는 보장이 아니다. 상대 통화와 제공자의 호가 및 자금 준비가 남는다.

다음 그림은 ChatGPT의 StableFX 그림과 Grok의 선택 쌍 및 Claude의 접근 구별을 내가 연결한 것이다. 가지는 기본 연결과 상품 이용의 별도 조건을 설명한다.

한국어:

```text
 [공개 메인넷과 RPC]
          |
          +---> [기본 체인 개발]
          |       지갑/가스/계약 실행을 확인한다
          |
          +---> [특정 금융 상품]
                  |
                  +---> [계정과 자격 승인]
                  +---> [지원 자산과 거래 조합]
                  +---> [호가/자금/결제의 실제 실행]
```

English:

```text
 [Public mainnet and RPC]
          |
          +---> [Base-chain development]
          |       Check wallet/gas/contract execution
          |
          +---> [Specific financial product]
                  |
                  +---> [Account and eligibility approval]
                  +---> [Supported asset and trade combination]
                  +---> [Actual quote/funding/settlement]
```

예를 들어 공개 RPC로 체인 ID를 읽고 테스트 계약을 만들었다고 StableFX의 실서비스용 API 접근 권한도 생기는 것은 아니다. 반대로 접근 권한을 아직 받지 못했다면 그 후보를 없애기보다 승인 의존성과 현재 사용할 대체 경로 및 모의 범위를 표시할 수 있다. 모의 호가를 실제 금융기관의 호가나 주최자의 승인으로 표현하지 않는다.

[RPC 문서](https://docs.arc.io/arc/references/rpc-endpoints.md)는 기본 Circle 주소에 대해 `No API key or credentials are required.`라고 설명하고, 다른 공급자는 자체 API 키를 요구할 수 있다고 덧붙인다. 이 조건은 해당 RPC 접속의 인증에 관한 것이다. 금융 상품의 API 계정 승인이나 거래 서명 권한을 면제한다는 뜻은 아니다. 서비스에 요청할 수 있는 권한과 지갑의 자금을 움직일 권한은 각각 해당 계정과 서명자를 확인해야 한다.

### 4.2 이용 자격: 자격 조건은 개발자, 최종 사용자, 기관과 서명자 가운데 누구에게 붙는지부터 정한다

Onramp의 지원 지역과 결제 수단, Mint의 기관 자격과 USYC(토큰화된 펀드 자산)의 참여 조건은 각각의 상품 규칙이다. 실제 서비스 이용에서는 KYB(Know Your Business, 사업자 확인), 서버 세션, 사용자 확인과 지역 조건을 구별해야 한다. USYC의 비미국 기관 대상 요건도 토큰 ARC의 개인 청구 자격을 정하는 규칙이 아니다.

한국 이용자의 특정 경로는 사용자의 국가와 서비스 자체의 지원 및 신청 계정 상태를 함께 확인해야 한다. 출시 발표에 Upbit가 등장하는 사실만으로 Upbit가 특정 날짜에 Arc 네트워크 출금을 제공한다고 할 수 없다. 거래소 자체의 네트워크 선택과 출금 조건을 읽고, 같은 이름의 자산이 다른 네트워크에 있다는 점도 구별해야 한다.

자격을 확인할 때에는 그 조건이 누구에게 붙는지 먼저 알아야 한다. [보존된 Onramp 문서](https://docs.arc.io/app-kit/onramp.md)는 서버 인증에 API 키를 요구하고, 일부 지급 수단을 활성화하려면 개발자 측의 KYB를 요구한다. 위젯은 최종 사용자의 신원 확인과 구매 처리를 담당한다고 설명한다. 개발자가 통합할 수 있다는 답과 최종 사용자가 해당 국가 및 지급 수단으로 구매할 수 있다는 답은 그래서 다르다. Onramp 문서는 시험 환경(sandbox)과 실서비스 환경(production)에 키를 따로 두라고 설명한다. 2026-10-07 실험에서는 같은 Testnet 키로 세션을 요청했을 때 `api.circle.com`과 `api-test.circle.com`이 모두 세션을 발급했다. 이 관측은 세션 발급 단계에 한정되며, 결제나 입금 단계에서 환경을 구분하는지는 확인하지 않았다. sandbox 위젯은 지역 KR과 은행 이체를 표시했지만 구매는 시도하지 않았다. 어느 쪽이든 시험 화면의 성공을 실서비스 자격의 확인으로 간주할 수는 없다.

[USYC 개요](https://developers.circle.com/tokenized/usyc/overview.md)는 대상을 `entities that are not U.S. Persons`라고 제한하고 추가 적격성 조건을 둔다. 이는 미국 밖에 있다는 조건 하나만으로 모든 개인이 참여할 수 있다는 뜻이 아니다. 토큰이 표준 계약 인터페이스로 표현된다는 사실도 펀드의 가입 및 상환 자격을 대신하지 않는다. 같은 토큰을 다루더라도 계약 조회, 보유 및 이동, 가입과 상환 중 어떤 행위를 하려는지 정해야 해당 조건을 읽을 수 있다.

아래 표는 Onramp와 USYC 문서 및 앞의 상품별 구별에서 내가 정리한 자격 확인 단위다. 각 행은 조건이 적용되는 주체와 행위의 관계이며, 사용자가 승인을 받았다는 기록은 아니다.

| 자격을 확인할 주체               | 확인할 행위와 조건                              | 다른 주체에게 그대로 옮기면 안 되는 판단                               |
| -------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| 앱을 운영하는 개발자 또는 사업자 | 서비스 인증, 실서비스 환경과 필요한 사업자 확인 | 개발자 계정의 승인으로 모든 최종 사용자의 이용이 허용되는 것은 아니다. |
| 앱의 최종 사용자                 | 거주 및 지원 지역, 신원 확인과 선택한 지급 수단 | 앱 설치나 지갑 생성만으로 구매 경로의 자격이 충족되지는 않는다.        |
| 기관 상품을 이용하는 조직        | 상품별 조직 자격, 계정 승인과 해당 거래의 조건  | 공개 체인의 계약 배포 가능성을 기관 상품의 가입 승인으로 쓰지 않는다.  |
| 지갑에서 거래를 승인하는 주체    | 해당 지갑의 서명 권한과 실행에 필요한 승인      | 서비스 API 인증만으로 임의 지갑의 자금을 사용할 수는 없다.             |

한국 이용자의 참가안에서는 이 주체들을 실제 구성에 대응시켜야 한다. 개발자가 한국에 있다는 사실과 최종 사용자가 한국 거주자라는 사실도 별도로 기록한다. 지원 국가의 목록이나 기관 요건이 필요한 행동에 어떻게 적용되는지 확인한 뒤, 허용된 경로와 승인 대기 중인 경로를 구분할 수 있다. 다른 자금 조달이나 시험 경로가 가능하더라도 그것이 제한된 상품의 자격을 대신한 것으로 설명해서는 안 된다.

### 4.3 실행 준비: 실행하려면 그 환경의 지갑, 가스로 쓸 USDC와 결과 확인 경로를 함께 준비한다

이용 권한과 자격이 맞더라도 지갑과 가스 자금, 접속할 네트워크가 준비되어야 실제 요청을 실행할 수 있다. 앞의 지원 범위 표가 제시한 지갑 설정과 대상 계약의 성공 및 실패 확인을 이용자의 선택 환경에 적용해야 한다.

가스 자금도 별도 접근 조건이다. [RPC 문서](https://docs.arc.io/arc/references/rpc-endpoints.md)는 테스트넷 USDC는 faucet에서, 메인넷 가스는 Circle 담당자를 통해 요청하라고 안내한다. 2026-10-07 실험에서는 테스트넷 faucet에 한 번 요청해 20 USDC를 받았다. 요청 간격의 제한은 한 번만 요청했으므로 확인하지 않았다. 새 상태 API에는 Mainnet의 Faucet 항목도 있다. 따라서 "메인넷에는 파우셋이 없다"고 단정하지 않는다. 이 항목만 보고 누구나 공개 무료 메인넷 자금을 받을 수 있다고 하지는 않는다. 실제 지급 방법과 자격이 남아 있다.

공식 글 연결: [Arc Mainnet Launches September 16, 2026](https://www.arc.io/blog/arc-mainnet-goes-live-on-september-16-2026) (2026-08-05, [공식 원문](https://www.arc.io/blog/arc-mainnet-goes-live-on-september-16-2026)). 메인넷 예고의 고지는 USDC 가스 자금을 확보하고 사용할 수 있어야 거래할 수 있다고 설명한다. 공개 무료 자금 지급이나 특정 계정의 자금 확보를 보장하지 않는다.

준비의 출발점은 어떤 행동을 어느 환경에서 완료하려는지를 정하는 것이다. 공개 RPC의 체인 정보를 읽는 작업과 서명하여 계약을 배포하는 작업은 필요한 자금과 권한이 다르다. Microgrants처럼 mainnet에서 작동하는 결과물을 요구한다면 testnet 지갑과 시험 자산만으로 준비가 끝나지 않는다. 반면 testnet 사용을 인정하는 프로그램에서는 시험 자산을 사용하는 이유와 실제 업무에서 시험한 범위를 명시해야 한다.

다음 표는 참가 준비에 필요한 항목을 내가 정리한 것이다. 한 행은 준비할 대상과 그 준비를 확인하는 결과다. 실제 배포와 오류 처리는 선택한 기능의 공식 문서 및 실행 기록을 기준으로 확인해야 한다.

| 준비할 대상      | 준비에서 정할 내용                                           | 준비 여부를 확인할 결과                                           |
| ---------------- | ------------------------------------------------------------ | ----------------------------------------------------------------- |
| 실행 환경        | 프로그램이 요구하는 체인과 RPC, 지갑의 선택 환경과 대상 계약 | 앱이 읽은 체인과 서명할 체인 및 배포 대상이 일치한다.             |
| 지갑과 승인 주체 | 직접 서명 또는 서비스 지갑의 승인 방식, 실행에 필요한 인증   | 사용할 계정으로 필요한 요청을 승인할 수 있다.                     |
| 자산과 가스      | 해당 환경의 자금 취득 경로, 필요한 거래 자산과 수수료 부담   | 실행할 지갑 또는 선택한 대납 경로에 필요한 자금이 준비되어 있다.  |
| 앱과 서비스 구성 | 선택한 SDK 및 예제 버전, 계약 주소와 서비스 환경             | 해당 구성으로 의도한 기능을 호출하고 결과를 조회할 수 있다.       |
| 결과 확인과 제출 | 배포 주소와 접근 링크, 거래 결과 및 실패 시 남는 기록        | 심사자가 결과물을 확인하고 참가자는 성공과 실패를 구별할 수 있다. |

자금 취득은 어디에 USDC를 보유했는지에서 시작한다. 다른 체인의 USDC가 있다면 선택한 이동 제품이 그 출발 및 목적 조합을 지원하는지 확인하고, 양쪽 처리와 Arc의 목적 지갑 도착을 구별한다. 법정화폐 구매를 쓰려면 앞에서 설명한 Onramp의 사용자 및 지급 수단 조건이 적용된다. 거래소 출금은 그 거래소가 Arc 네트워크를 실제 지원하는지 확인해야 한다. 이들은 확인할 경로의 예시이며, 이번 연구가 사용자의 자금을 확보하거나 모든 경로를 시험했다는 뜻은 아니다.

또한 업무에 사용할 금액과 실행 수수료를 함께 준비해야 한다. [Microgrants 공고](https://community.arc.io/public/events/arc-microgrants-f8tijfjhyq)는 `USDC on Arc to deploy and transact`가 필요하다고 적는다. 단순히 다른 네트워크의 잔액이나 시험 자산을 보유했다는 답으로는 이 조건을 충족했는지 알 수 없다. 선택한 가스 대납을 이용한다면 대납의 활성화와 적용 범위도 확인해야 한다. 예상 비용은 이번 원고에서 고정 금액으로 정하지 않고 실제 실행 조건과 견적에 따라 확인한다. 2026-10-07 테스트넷 실험에서는 같은 계약을 두 번 배포한 수수료가 각각 0.003920325 USDC와 0.0050964225 USDC였고, USDC 전송 한 건의 수수료는 0.00042 USDC였다. 테스트넷에서 거래마다 한 번 본 값이므로 메인넷 비용으로 옮기지 않는다.

마지막으로 읽기 응답, 서명 요청의 접수, 체인에 포함된 거래와 앱에서 확인한 업무 결과를 연결해야 한다. 계약 주소를 얻었다고 앱의 핵심 기능이 작동했다고 결론내리지 않고, 거래 해시가 생겼다고 최종 업무가 끝났다고 하지 않는다. 개발 접근 설명이 설명한 영수증과 상태 및 실패 처리를 필요한 범위까지 확인하면, 준비가 끝난 부분과 실제 실행으로 더 확인할 부분을 구별할 수 있다. 제출에 쓸 계약을 탐색기에서 소스 검증하는 일도 따로 확인한다. 2026-10-07 실험에서 첫 배포의 소스 검증은 도구가 자동으로 고른 컴파일러(solc 0.8.37)에서 실패했다. 탐색기의 컴파일러 목록에는 0.8.37이 없었고, 0.8.36으로 다시 배포하자 검증을 통과했다. 이 구별은 뒤의 제출 요건에서 무엇을 작동 결과물로 보여줄지 정하는 데 쓰인다.

## 5. 사용 현황: 자금, 거래와 기관 참여는 실제 이용을 어디까지 보여주는가

제공과 접근 조건은 사용 가능성을 설명한다. 실제 이용을 설명하려면 자금 규모와 거래 활동을 따로 읽고, 그 관측이 고객 업무와 기관 참여를 어디까지 뒷받침하는지 확인해야 한다.

| 관측 대상         | 직접 설명하는 내용         | 실제 업무와 성과를 판단하려면 필요한 내용 |
| ----------------- | -------------------------- | ----------------------------------------- |
| 예치 자산         | 집계 기준에 따른 예치 규모 | 자금의 주체, 목적과 유지 기간             |
| 스테이블코인 공급 | 집계 기준에 따른 유통 공급 | 보유 목적과 실제 사용 경로                |
| 기간별 거래량     | 정해진 기간의 교환 규모    | 거래 종류, 반복 이용과 이용 동기          |
| 기관 참여 발표    | 발표된 참여 방식과 단계    | 현재 운영 범위와 실제 업무 기록           |
| 고객의 실행 기록  | 확인한 업무와 처리 결과    | 비용, 오류와 대안 대비 변화               |

각 행은 관측 대상의 종류다. 필요한 근거를 비교하며, 고객의 실행 기록까지 모두 확보했다는 뜻은 아니다.

### 5.1 자금 규모: TVL은 예치 자산을, 스테이블코인 시가총액은 유통 공급을 측정하며 둘을 더하지 않는다

TVL(Total Value Locked)은 프로토콜에 예치된 자산의 가치를 집계한 값이다. 스테이블코인 시가총액(stablecoin market cap)은 체인에서 발행되거나 이동한 스테이블코인의 유통 공급과 가격을 기준으로 계산한다. 두 지표는 예치 자산과 유통 공급을 각각 설명한다.

[DefiLlama의 정의](https://docs.llama.fi/analysts/data-definitions)는 TVL에서 차입금과 중복을 구별한다. 예치 자산과 스테이블코인 공급은 서로 다른 집계이므로 같은 이름의 자산이 포함되더라도 두 값을 하나의 총액으로 더하지 않는다.

집계기관의 조정 설명이 Arc의 모든 계산을 감사한 결과는 아니다. 어떤 코드와 주소, 가격과 제외 옵션이 실제 값에 적용됐는지 재현하려면 추가 자료가 필요하다. 지표 정의를 읽는 일은 수치를 해석할 출발점이며 모든 계산의 정확성을 자동으로 확인하는 절차가 아니다.

[다시 읽어 보존한 화면](https://defillama.com/chain/arc)은 아래 값을 표시했다. 직접 HTML 요청은 403이었고 웹 도구의 반환 텍스트를 보존했다. 차트 이미지와 집계 코드를 검토한 것은 아니다.

| 화면 항목        | 보존한 표시값 | 이 값으로 답하는 질문                              |
| ---------------- | ------------- | -------------------------------------------------- |
| DeFi TVL         | \$540.61m     | 해당 화면의 정의에 따른 예치 자산 가치는 얼마인가? |
| Stablecoins Mcap | \$511.93m     | 체인별 스테이블코인 공급의 집계 가치는 얼마인가?   |

단위 `m`은 million이며 예를 들어 \$540.61m은 \$540,610,000 = 540.61 * 1,000,000이다. 이 표와 다음 거래량 표는 고정된 조회의 표시값이다.

예치 자산과 공급을 함께 읽으면 서로 다른 질문을 만들 수 있다. 공급 집계는 체인에 얼마나 많은 스테이블코인이 유통되는지를, TVL은 집계 대상 프로토콜에 어느 정도의 자산 가치가 예치되었는지를 묻는다. 공급된 자산이 모두 같은 프로토콜에 예치되는 것도 아니고, 예치 자산의 구성도 스테이블코인만이라고 가정할 수 없다. 따라서 두 값의 차이를 곧바로 미사용 자금이나 별도의 고객 수요로 해석하려면 자산 구성과 집계 범위를 더 확인해야 한다.

### 5.2 거래 활동: DEX 거래량은 정해진 기간의 교환 규모이며 이용자 수나 지급 업무를 대신하지 않는다

DEX(Decentralized Exchange, 탈중앙화 거래소)의 거래량은 일정 기간의 교환 규모를 다룬다. 앞의 자금 규모가 보유 또는 공급을 설명한다면, 거래량은 정해진 시간 동안 발생한 교환의 흐름을 설명한다.

[DefiLlama의 정의](https://docs.llama.fi/analysts/data-definitions)는 DEX 거래량에서 두 거래 다리의 중복과 단순 송금 및 예치와 출금을 구별한다. 인센티브 목적의 비정상 거래도 조정한다고 설명한다. 따라서 Claude가 지적한 인센티브 문제를 설명하면서 "집계에는 모두 그대로 포함된다"고 단정하면 정의를 무시하게 된다.

같은 보존 화면에서 거래량은 다음과 같이 표시됐다. 앞의 자금 규모와 같은 조회에 포함된 값이지만, 거래량에는 집계 기간이 있으므로 잔액과 구별해서 읽는다.

| 화면 항목        | 보존한 표시값 | 이 값으로 답하는 질문                    |
| ---------------- | ------------- | ---------------------------------------- |
| DEXs Volume, 24h | \$36.18m      | 해당 집계의 24시간 교환 규모는 얼마인가? |
| Volume, 7d       | \$382.23m     | 같은 화면의 7일 거래 집계는 얼마인가?    |

앞의 자금 규모와 이 거래량을 ChatGPT와 Claude 답변의 수치와 비교할 때도 조회 시점을 유지해야 한다. ChatGPT 답변의 TVL \$543.77m와 24시간 DEX \$69.09m, Claude의 10월 4일 약 \$540m를 동일한 시각의 서로 모순된 답으로 합치지 않는다. 역사 API와 현재 화면은 관측 시점 및 필드가 다를 수 있다.

화면은 Morpho Blue, Aave V4와 Uniswap 등을 함께 표시한다. 이는 외부 집계에 앱과 자금 항목이 존재한다는 근거다. 해당 앱의 모든 계약과 실제 거래를 재검증한 것은 아니다. 계약별 잔액과 거래, 앱 자체 기록을 읽으면 더 구체적인 사용을 설명할 수 있지만 이번 수치를 고객의 정기 업무량으로 바꾸지는 않는다.

거래량을 해석할 때에는 무엇을 거래로 센 값인지도 중요하다. DEX 거래량은 교환의 규모이므로 지갑 간 송금이나 기업의 모든 지급을 대신하는 지표가 아니다. 같은 자금이 반복 교환되어 기간의 거래량을 만들 수 있으며, 높은 거래량만으로 서로 다른 고객이 얼마나 이용했는지 알 수는 없다. 반대로 고객의 지급 앱이 DEX 교환을 하지 않는다면 DEX 거래량만으로 그 앱의 사용을 평가하기도 어렵다. 필요한 업무에 맞는 계약, 이벤트와 이용 기록을 선택해야 한다.

기간을 비교하는 질문도 자료의 범위를 따라야 한다. 같은 화면의 짧은 기간과 긴 기간 집계는 서로 겹칠 수 있으므로 독립된 실적처럼 더하지 않는다. 증가나 감소를 설명하려면 같은 정의의 연속 관측이 필요하고, 증가의 원인을 설명하려면 그 기간에 어떤 앱과 자산 및 이용자가 활동했는지를 더 읽어야 한다. 이번 표시값은 그러한 후속 질문을 만드는 출발점이다.

### 5.3 고객 업무: 문제 해결과 경제적 효과는 자금과 거래 지표가 아니라 고객의 업무 기록으로 판단한다

예치금이 많아도 그 돈을 누가 어떤 목적과 기간으로 넣었는지는 별도 질문이다. 시드 자금, 인센티브와 투기적 교환 또는 실제 업무가 함께 있을 수 있다. 반대로 인센티브가 있다는 이유로 모든 사용을 무가치하다고 판정하는 것도 근거가 부족하다. 거래를 분류하고 고객의 실제 업무 및 반복 사용을 읽어야 한다.

다음 그림은 ChatGPT의 사용 증거와 Claude의 유입 동기, Grok의 계약 미확인을 내가 연결한 것이다. 상자는 서로 다른 질문이며 점선은 추가 증거가 필요한 연결이다.

한국어:

```text
 [자산 잔액/TVL]       [기간별 거래/수수료]
         |                    |
         +---------+----------+
                   :
                   : 계약/로그/주소의 추가 대조
                   v
           [주소와 앱의 실제 행위]
                   :
                   : 고객/목적/반복 업무의 추가 근거
                   v
           [사용자 문제의 해결과 채택]
                   :
                   : 비용/대안/순증의 추가 근거
                   v
           [Arc의 기여와 경제적 효과]
```

English:

```text
 [Asset balances/TVL]       [Period trades/fees]
          |                        |
          +------------+-----------+
                       :
                       : More checks of contracts/logs/addresses
                       v
               [Actual address/app actions]
                       :
                       : More evidence of customer/purpose/repeat work
                       v
               [Problem resolution and adoption]
                       :
                       : More evidence of costs/alternatives/net additions
                       v
               [Arc contribution and economic effects]
```

TVL과 거래량을 더해 총 경제 효과를 구하지 않는다. 같은 자산의 보유와 반복 거래가 다른 단위와 기간으로 측정되기 때문이다. 실제 사업 참가안의 성과도 "거래를 몇 번 만들었다"와 "어떤 업무의 비용 또는 오류를 줄였다"를 각각 기록해야 비교할 수 있다.

[Tameion의 실제 사용 설명](https://tameion.thecanteenapp.com/)은 작은 사업이나 자기 사업의 문제도 인정하며, 청구서와 외주 지급 같은 업무를 예로 든다. 이를 참가안에 적용하는 설명용 사례로, 청구서를 읽고 지급을 제안하는 에이전트를 생각할 수 있다. 체인 거래 기록은 자금 이동을 보여주지만 청구서가 실제 의무였는지, 올바른 수취인을 골랐는지와 같은 질문에는 업무 기록이 필요하다. 같은 지급을 반복하지 않았는지와 사람의 확인 부담이 줄었는지도 별도로 확인해야 한다.

이때 필요한 자료는 결과물의 주장에 맞추어 정한다. 처리한 청구서와 그 상태, 승인한 사람 또는 정책, 지급 결과를 연결하면 어떤 업무를 수행했는지 설명할 수 있다. 처리 전후의 시간과 오류, 기존 방식으로 수행했을 때의 결과를 비교하면 개선 효과를 평가할 수 있다. 여기서 제시한 연결은 내가 사업 성과의 근거를 설명하기 위한 것이며, 실제 이용자를 관측하여 얻은 성과는 아니다. 고객 업무의 확인과 개선 효과의 측정, Arc를 사용한 데 따른 기여를 각각 기록해야 결과가 과도하게 일반화되지 않는다.

### 5.4 기관 참여: 발표 명단은 운영과 탐색을 함께 담으므로 기관별 현재 운영은 미확인으로 남긴다

고객 업무를 확인할 때 기관 명단은 조사 대상을 알려줄 수 있다. 그러나 명단에 등장한다는 사실과 현재 운영하거나 탐색하고 있다는 설명은 같은 근거가 아니다. 기관 이름과 함께 참여 방식 및 단계를 읽어야 한다.

출시 발표의 검증자는 `phased rollout`로 참여한다고 설명한다. 사업 및 기관 목록은 `live on or exploring`이라고 적는다. 앞의 명단은 지정 또는 기대의 근거이고, 뒤의 목록은 운영과 탐색을 함께 포함한다. 이름 하나만 남기고 동사를 버리면 확정 운영 고객 목록처럼 읽히게 된다.

공식 글 연결: [Arc Mainnet Is Here: The Economic OS for the Internet Is Now Live](https://www.arc.io/blog/arc-economic-os-internet) (2026-09-16, [공식 원문](https://www.arc.io/blog/arc-economic-os-internet)). 출시 글의 검증자 목록은 단계별 참여 계획을 포함한다. 기관별 현재 서명, 유료 업무와 거래 규모는 명단만으로 확인하지 않는다.

발표는 Circle과 함께 BlackRock, DTCC(Depository Trust & Clearing Corporation), Galaxy, ICE, Mastercard, MoneyGram, SBI Group, Standard Chartered, Sumitomo Corporation, Visa와 Worldpay를 창립 코호트에 적는다. Worldpay 옆에는 현재 Global Payments라는 설명도 붙인다. 이것은 발표의 이름과 표현을 보존한 것이며 법인의 변경 이력을 별도로 검증한 결과는 아니다. 이 이름들을 현재 합의 집합의 기관별 투표권 표로 읽지 않는다.

검증자가 현재 서명하는지 알려면 고정 시점의 합의 집합과 서명 또는 제안자 주소를 읽고 그 주소를 해당 기관에 대응해야 한다. 블록의 수수료 수혜자 주소를 확인해도 기관 소유와 서명을 동시에 확인한 것은 아니다. 프로토콜의 초기 설정과 가치 흐름의 수혜자 설명도 이 구별을 유지한다.

파트너의 실제 사업에는 고객별 거래 종류, 기간과 규모 및 상대 주체의 운영 기록이 필요하다. Visa의 전체 스테이블코인 지급을 연 단위로 환산한 실적을 Arc 단독의 연간 실적으로 귀속하면 안 된다. 체인별 구분이 없는 전체 값으로 Arc의 기여를 계산할 수 없기 때문이다. CPN(Circle Payments Network)의 전체 처리량과 연환산 수치도 같다. 그 수치는 Arc 경로의 현재 기업 지급량이 아니다. 상대 회사의 발표도 계획과 실제 운영을 구별해서 읽는다.

이 연구는 명단을 보존하고 참여 동사를 설명한다. 기관별 현재 서명과 업무량은 미확인으로 남긴다. 같은 보도자료를 여러 서비스가 인용한 일치가 그 미확인을 해소하지 않는다.

## 6. 참가 조건: 프로그램의 목적, 일정과 제출 및 지급 요건은 어떻게 다른가

각 행은 아래 일정과 제출 요건에 등장하는 프로그램이다. 상세 마감과 영상 길이는 해당 표와 본문에 유지한다. 미확인은 이번 원고의 확인 범위를 뜻한다.

한국어:

```text
 [필요한 기능과 실행 환경]    [참가자의 자격과 실행 준비]
             |                            |
             +-------------+--------------+
                           |
                           v
                 [참가안의 조건 대조] <--- [프로그램별 조건]
                           |               일정 / 제출 / 선정 / 지급
             +-------------+--------------+
             |                            |
             v                            v
     [접수 가능성 판단]          [선정과 지급의 남은 조건]
```

English:

```text
 [Needed function and environment]   [Participant eligibility and readiness]
                 |                                      |
                 +------------------+-------------------+
                                    |
                                    v
                     [Compare proposal conditions] <--- [Program conditions]
                                    |                   Dates / Submission /
                                    |                   Selection / Payment
                 +------------------+-------------------+
                 |                                      |
                 v                                      v
     [Assess ability to submit]      [Remaining selection and payment conditions]
```

화살표는 참가안을 검토하는 관계를 나타낸다. 제품 상태와 접근 조건의 확인 항목을 프로그램별 조건과 대조하여 접수 가능성과 선정 및 지급의 남은 조건을 함께 살핀다. 실제 접수, 선정과 지급의 완료를 나타내지 않는다.

### 6.2 참가 일정: 목록의 행사 기간은 제출 마감과 다르며, 마감은 공고 본문의 시각을 따른다

[Microgrants 공고](https://community.arc.io/public/events/arc-microgrants-f8tijfjhyq)는 목록의 10월 15일 표시와 별개로 10월 14일 23:59 ET 제출을 적는다. [Tameion 주최 본문](https://tameion.thecanteenapp.com/)은 Arc House의 10월 10일 목록 끝과 별개로 10월 17일 11:59 PM ET 제출을 적는다. 목록의 끝을 제출 시각으로 복사하지 않는다.

| 프로그램                 | 서로 다른 날짜와 사건                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------- |
| Arc Microgrants          | 제출 2026-10-14 23:59 ET = 10-15 12:59 KST. 심사 결정은 공고상 10월 21일까지다.                         |
| Tameion Agents Hackathon | 주최 제출 2026-10-17 23:59 ET = 10-18 12:59 KST. 목록 기간과 다르다.                                    |
| Arc Acceleration Season  | 지원 9월 22일 종료, 운영기관의 시작 9월 28일과 Demo Day 11월 첫 주다. Arc House 목록은 10월 24일까지다. |
| Circle Developer Grants  | 기존 공식 프로그램 안내를 확보했다. Questbook의 현재 Open 및 회차와 마감 표시는 이번에 미확인이다.      |

두 마감 날짜에서 ET는 UTC-4이고 KST는 UTC+9이므로 13시간을 더한다. 10월 14일 23:59 + 13시간 = 10월 15일 12:59이며, 10월 17일에도 같은 방식으로 다음날 12:59가 된다. 목록 날짜의 생성 원인이 이 시간대라고 추정하지는 않는다.

[Acceleration의 운영기관 본문](https://crecimiento.build/blog/arc-acceleration-season-en)은 Demo Day를 11월 첫 주라고 적는다. Claude 답변의 11월 5일 스니펫을 확정 날짜로 올리지 않는다. 정상 지원 마감이 지났다는 사실과 예외적 추가 참가의 가능성은 별도 질문이다. 공개 신청 링크가 남아 있다는 사실도 승인을 뜻하지 않는다.

일정을 참가안에 적용하려면 마감 전에 끝나야 할 행동도 함께 적어야 한다. 계정 승인, 자금 확보와 배포, 실제 사용자 시험 및 제출 자료 준비가 필요한 안이라면 각 행동의 선행 조건을 확인한다. 주최가 제출을 받는 기간이 남았더라도 필요한 접근 권한이 그 안에 확보된다는 보장은 없다. 반대로 지원 마감과 프로그램 운영 기간이 다르면, 이미 선발된 팀의 개발 진행을 신규 지원 가능성으로 읽어서는 안 된다.

따라서 일정은 참가 후보를 비교하는 자료와 작업 순서를 정하는 자료로 함께 쓰인다. 신청과 제출 중 어떤 행동의 마감인지 확인하고, 그 행동에 필요한 승인과 실행이 어디까지 준비되었는지 대조한다. 남은 준비의 소요 시간은 실제 응답과 실행 기록으로 확인할 항목이며, 이번 원고가 임의의 기간을 부여해 참가 가능성을 확정하지 않는다.

### 6.3 제출 요건: 프로그램마다 요구하는 실행 환경, 결과물과 실제 사용의 단계가 다르다

각 프로그램의 일정에 맞추어 제출하려면 실행 환경과 결과물 요건도 충족해야 한다. 아래 표는 앞의 일정표와 같은 프로그램의 이용 및 참여 요구를 비교한다.

| 프로그램                 | 제공 환경과 참여 요구                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Arc Microgrants          | 작동하는 mainnet 배포와 공개 repo가 필요하다. testnet-only는 부적격이다.                                                                  |
| Tameion Agents Hackathon | 초대 및 등록 조건이 있으며 공개 repo와 3분 미만 영상이 필요하다. 실제 사업의 test USDC 사용도 인정하며 mainnet 실사용을 더 높게 평가한다. |
| Arc Acceleration Season  | Latam의 실제 시장 또는 closed beta 스타트업과 기술 공동창업자 등을 대상으로 한다. testnet Build에서 mainnet Ship으로 이어진다.            |
| Circle Developer Grants  | 신청 검토와 milestone 승인 및 지급 조건은 다음 절에서 다룬다.                                                                             |

Microgrants는 작동하는 mainnet 결과물을 요구하지만 회사와 고객 실적을 필수로 요구하지 않는다고 설명한다. Tameion은 test USDC도 인정하면서 실제 사업의 사용을 강조한다. 그러므로 같은 데모가 두 프로그램에서 같은 요건을 충족한다고 볼 수 없다. mainnet 여부와 실제 사업 사용이라는 서로 다른 질문을 각각 확인해야 한다.

Tameion은 자기 사업이나 작은 사업의 실제 문제가 있어도 된다고 설명하며 synthetic dataset은 실제 사용으로 인정하지 않는다. 기존 프로젝트를 계속한다면 행사 기간에 추가된 기능과 새 사업 이용자의 증가를 구별해 제출하라고 한다. 주최의 다섯 Requests for Builders는 시작할 문제의 제안이며 강제 트랙이 아니다. 후보를 그 다섯 범주만으로 사전 제한하지 않는다.

제출 자료도 프로그램이 판단하려는 대상에 맞추어 구성해야 한다. [Microgrants 공고](https://community.arc.io/public/events/arc-microgrants-f8tijfjhyq)의 `Build first, then submit`는 제출 당시 이미 작동하는 mainnet 결과물을 전제로 한다. 공고는 열어볼 수 있는 배포 링크와 공개 저장소, 프로젝트의 기능 및 Arc 사용을 설명하는 짧은 글과 공개 빌더 프로필을 요구한다. 따라서 앞으로 만들겠다는 계획과 화면 목업만으로는 공고가 요구하는 현재 결과물을 대신할 수 없다.

[Tameion 제출 안내](https://tameion.thecanteenapp.com/)는 공개 저장소와 녹화 영상을 필수로, 작동하는 제품 링크를 권장 사항으로 구별한다. 심사자는 제출 이후 참가자가 설명해 주지 않는 상황에서 저장소와 제공된 제품을 검토한다. 에이전트가 무엇을 결정하고, 그 결정이 어떤 실제 사업의 업무와 자금 이동에 연결되는지를 제출 자료에서 확인할 수 있어야 한다. 시험 자산을 사용했다면 그 사실을 밝히면서 실제 사업 문제를 시험한 범위를 보여주는 방식이 필요하다.

기존 프로젝트를 계속하는 경우에는 시작 상태와 행사 기간의 변화가 중요하다. Tameion은 새 기능과 새 사업 이용자의 증가를 모두 구별하므로 기존의 전체 기능과 누적 실적을 행사 기간의 성과로 제출해서는 안 된다. 반면 Microgrants는 공고상 해커톤을 이어 만든 결과물도 허용하되 이미 Circle 또는 Arc 프로그램으로 지원받은 작업은 제외한다. 같은 프로젝트라도 기존 지원 이력과 이번에 추가한 작업을 기록해야 프로그램별 요건을 비교할 수 있다.

[Acceleration 설명](https://community.arc.io/public/events/arc-acceleration-season-vanemu91dk)의 testnet 개발과 mainnet 출시도 제출 순간의 상태 하나로 합치기 어렵다. 공고가 설명한 개발 단계에서는 작동하는 시험 시제품을 만들고, 출시 단계에서는 실제 운영 환경에 배포하여 성능과 비용 및 예외 상황을 다룬다. 이는 프로그램의 지원 아래 진행하는 개발 과정이며, 이미 mainnet 결과물을 제출하는 Microgrants와 역할이 다르다. 프로그램이 요구하는 결과물과 그 결과물을 만드는 시점을 함께 읽어야 한다.

과거 공고까지 비교하면 작동 시제품, 실제 사용과 사업 출시를 같은 요구로 합칠 수 없다는 점이 더 분명해진다. 아래 표는 각 프로그램이 판단하려는 단계를 내가 비교한 것이다. 과거 행사의 요구를 현재 다른 프로그램의 자격으로 옮겨 적용하지 않는다.

시제품을 만들었다는 근거, 실제 이용자가 있다는 근거와 출시 후 업무를 안정적으로 처리한다는 근거는 각각 확보해야 한다. 지원 프로그램이 어느 단계를 보려는지에 따라 제출 자료를 달리 구성하며, 이 차이를 현재 접수 자격과 마감 확인에 더해 적용한다.

### 6.4 선정과 지급: 접수 뒤에도 검토, 수령자 확인과 목표 승인이 남으므로 지급은 따로 확인한다

앞의 제출 요건을 충족하여 접수한 뒤에는 주최자의 검토와 선정, 수령자를 위한 확인 또는 합의한 목표의 달성 및 승인 과정이 남는다. 이 과정은 프로그램마다 다르므로 무엇을 평가하고 어느 조건에서 지급하는지를 각각 읽어야 한다.

여기서 다루는 선정 지원금은 가치와 토큰 설명이 설명한 포인트 및 토큰 권리와도 다르다. 무료 시험 자산과 선정 지원금 및 향후 토큰을 하나의 보상으로 합치지 않는다.

[Microgrants의 절차](https://community.arc.io/public/events/arc-microgrants-f8tijfjhyq)는 제출의 완결성과 프로그램 적합성을 먼저 확인하고, 선별한 프로젝트를 평가하여 묶음으로 결정한다고 설명한다. 접수 기간 중에도 검토가 진행되지만 먼저 제출했다고 자동 선정되는 것은 아니다. 공고가 제시한 평가 대상은 Arc와의 관련성, 기술적 신뢰성, 결과물의 품질과 계속 발전시킬 가능성이다. 회사나 기존 고객 실적을 필수로 요구하지 않는다는 조건과 함께 읽으면, 이 프로그램이 초기의 작동 증명을 평가한다는 의미를 이해할 수 있다.

익명 또는 가명으로 제출할 수 있다는 조건도 선정 뒤의 확인과 구별해야 한다. 공고는 `Verification happens only after conditional selection`이라고 적고, 수령자를 위한 비공개 확인을 설명한다. 따라서 공개적으로 신원을 밝히지 않아도 제출할 수 있다는 설명이 지급 확인을 생략한다는 뜻은 아니다. 지급 자산은 Arc의 USDC이므로 수신 가능한 지갑도 필요하다. 공고의 조건에 따른 확인과 실제 지급 기록이 있어야 선정에서 수령까지 이어졌다고 말할 수 있다.

[Developer Grants의 절차](https://www.circle.com/grant)는 신청서에 사업, Circle과 Arc의 통합, 제품 로드맵과 제안하는 마일스톤(milestone, 합의하여 달성 여부를 확인하는 개발 및 사업 목표)을 담도록 한다. Grants 팀이 초기 적합성을 검토하고, 일부 신청은 Circle Ventures와 제품 및 사업개발 팀의 의견을 포함하는 기술 검토로 진행된다. 공고는 계속 진행할 최종 후보에게 적용되는 추가 심사(screenings)의 완료도 요구한다. 선정되면 로드맵에 맞춘 목표와 통합 약속을 합의한다. 이 절차는 이미 제출한 작은 결과물에 대한 지원과 달리 이후 개발의 이행을 함께 다룬다.

지급도 신청이나 선정만으로 완료되지 않는다. 같은 안내는 `Payments are released as milestones are met and approved.`라고 적는다. 합의한 목표의 달성과 승인에 따라 지급되며, 최종 목표를 완료한 뒤 추가 지원을 신청할 수 있다고 설명한다. 목표의 구체적인 내용과 증명 자료 및 승인 여부는 각 팀의 합의와 실제 진행 기록에서 확인해야 한다. 일반 안내를 확보했다는 사실만으로 현재 회차의 접수 상태나 특정 팀의 지급일을 확정할 수는 없다.

Tameion은 제출 마감 뒤 비동기 심사로 결과물을 검토한다고 설명한다. [심사 안내](https://tameion.thecanteenapp.com/)는 에이전트의 결정 수준과 실제 사용을 함께 중시하고, Circle 도구의 효과적인 활용과 새로운 접근도 평가한다. 테스트넷 사용도 인정하지만 실제 고객의 mainnet 사용을 더 높게 평가한다는 차이는 앞의 제출 요건과 연결된다. 이는 평가의 방향이며 어느 팀이 선정되거나 지급받았는지를 보여주는 결과 기록은 아니다. 이후 자금과 지원 및 협력을 소개하는 문구도 특정 참가자에게 후속 지원이 확정되었다는 뜻으로 쓰지 않는다.

## 7. 판단 범위: 무엇을 확인했고 어떤 판단을 후속 조사로 남기는가

지금까지의 설명을 종합하여 확보한 근거로 가능한 판단과 추가 관측이 필요한 판단을 나눈다. 답변이 제시한 추가 조사 대상도 확인 범위와 미확인 이유를 구별해 정리한다.

### 7.1 확인 범위: 공개 출시와 기능별 조건은 설명할 수 있고, 이용자의 메인넷 실행과 고객 성과는 남는다

현재 근거로 가능한 답은 다음과 같다. 기본 네트워크의 공개 출시와 읽기 응답을 근거 범위에 맞게 설명할 수 있으며, 기능별 자산과 계정 자격 및 실제 사용의 확인은 별도로 남는다. 미래 기능과 토큰의 계획도 현재 제공 및 개인 권리와 구별해야 한다. 참가안은 그 조건을 사용해 "필요한 기능을 이 기간에 이 참가자의 자격으로 실제 사용할 수 있는가?"를 확인해야 한다. 이 연구는 2026-10-07에 테스트넷에서 시험 계약을 배포하고 시험 USDC를 보냈지만(2.2(실행 환경)), 사용자의 제품 배포와 메인넷 자금 이동 또는 신청을 완료하지는 않았다.

| 네트워크 연결과 실행  | 선택 환경의 RPC, 가스 취득과 계약 배포 및 실패 영수증을 확인한다. 2026-10-07 테스트넷 실험이 RPC 연결, faucet, 계약 배포와 호출의 성공을 확인했고(2.2), 실패 영수증과 메인넷 실행은 남았다. | 사용자의 환경에서 실제 성공과 복구를 확인하면 해당 경로의 실행 상태를 설명할 수 있다. |
| 금융 상품의 접근      | 계정 승인, 지원 자산과 호가 및 자금과 결제 기록을 확인한다.                                                                                                                                 | 해당 참가자의 자격과 거래 조합이 열렸을 때 접근과 실행의 답을 바꾼다.                 |
| 기관과 고객의 운영    | 검증자 집합 및 기관-주소 대응, 고객별 업무와 기간을 읽는다.                                                                                                                                 | 명단을 넘어 고정 시점의 서명 또는 실제 업무를 확인했을 때 그 범위만 채택한다.         |
| 미래 기능             | 릴리스와 배포 주소 및 계정 접근, 실제 호출을 대조한다.                                                                                                                                      | 문구 삭제나 로드맵 날짜만으로 제공 상태를 바꾸지 않는다.                              |
| 참가 기간과 운영 변경 | 주최의 접수 조건과 마감 변경, 주소 공지의 시행을 확인한다.                                                                                                                                  | 행사 표시가 아니라 해당 행동의 실제 요구와 시행을 갱신한다.                           |

이 표는 내가 현재 근거의 간격에서 도출한 다음 질문이다. 가치가 낮을 것으로 예상되는 후보를 제거하는 표가 아니다. 마감과 주소 변경, 선행 승인 및 접근 종료에 따라 확인 순서를 정할 수 있다.

### 7.3 미확인 사항: 추가 조사 대상과 확인 한계를 구별한다

| 답변이 보완한 내용                                                                    | 확인 범위와 남은 질문                                                                                                                                                         |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ChatGPT의 Portal과 자산, FX 및 RWA(Real-World Assets, 현실 자산의 토큰화) 출시 이정표 | ChatGPT가 제시한 상세 시간선이다. 이번에 다시 읽은 공식 사건과 ChatGPT 답변의 나머지 보고를 구별한다.                                                                         |
| ChatGPT의 Aave V4 변경 기록 및 Morpho 앱 거래와 위험 자료                             | 모델이 제시한 추가 조사 대상이다. 앱 자체 계약 및 거래를 모두 재확인하지 않았으므로 현재 확정 실적으로 확대하지 않는다.                                                       |
| Claude의 시드 자금, 거래 구성과 서로 다른 첫날 거래 집계                              | 모델이 제시한 추가 조사 대상이다. 정의와 시간 창을 확인해야 하므로 두 값을 평균내거나 인센티브 비중을 확정하지 않는다.                                                        |
| Grok의 탐색기와 부가 자료 및 Questbook 표시                                           | 이번 RPC 보존 응답과 모델의 화면 보고, 빈 검색본을 구별한다.                                                                                                                  |
| Visa의 전체 스테이블코인 실적과 기관 협력                                             | Arc 체인별 실적을 읽지 않아 Arc 단독 수치로 채택하지 않는다.                                                                                                                  |
| Encode 및 ETH 행사                                                                    | 이번 보충에서는 확보한 공고의 목적과 제품 방향을 참가 조건에 반영했다. 과거 행사의 상세 바운티와 현행 회차의 자격 및 마감은 이 보충만으로 확정하지 않으며 관련 조건을 남긴다. |
| 버그 바운티와 Builders Fund                                                           | 추가 조사 후보로 구별한다. 최신 회차와 자격 및 마감을 확인한 뒤 참가안에서 이어 판단할 수 있다.                                                                               |
| 포스트 양자 보호와 에이전트 신원 표준 및 한국 거래소 출금                             | 상세 기술 및 경로를 직접 확인할 후속 질문으로 남긴다. 특정 문서의 표기를 전체 구현의 전수 상태로 쓰지 않는다.                                                                 |

후속 참가안에서는 확인한 제공 범위와 이용 자격을 출발점으로 삼고, 마감과 선행 승인 및 접속 변경에 맞추어 남은 질문을 확인해야 한다. 보류한 설명은 그 질문에 필요한 근거가 확보되었을 때 해당 범위에서 다시 판단할 수 있다.
